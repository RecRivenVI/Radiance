## 区块加载共享锁修复与剩余长帧

使用者报告：将单向几何全部切换为双向后，严重掉帧主要发生在区块加载期间。2026-10-15 的[项目内诊断](../research/investigation-chunk_loading_lock_contention.md)已确认拓扑准备占据区块共享锁，造成主线程超过百毫秒的等待。[定向修复](../research/investigation-chunk_loading_lock_fix.md)已将独立 CPU 准备移出锁，保留所有者、代际、版本与 GPU 退休保护；没有关闭几何规则或减少画质。

使用者于 2026-10-12 暂停调查，并于 2026-10-15 明确恢复此专项，授权只读复制 Prism 最新世界到项目内验证实例。当前只测量加载、网格重建及其直接调用链，其他性能方向不扩大。机器指标使用实际设置与产物身份，轻微环境波动单独记录。

2026-10-15 的查询规则候选在使用者手工观察中仍复现加载严重卡顿，视觉无明显问题不等于性能通过。对应产物、配置及只读日志证据见[本轮手工反馈](status-current.md#成像与传光收敛)。诊断第二轮 F3+A 后发生设备丢失，无 F3+A 的修复前对照也在初次加载失败，该组已停止，没有自动重跑。随后使用者重新授权默认 GPU 采集配置下的候选复测，单次 60 秒世界流程正常完成，关键主线程锁等待未再达到百毫秒，见[复测证据](../research/investigation-chunk_loading_with_gpu_capture.md)。此前故障、GPU 根因与完整 G3 仍独立保留，暂无同一诊断条件的严格前后收益。

最近的[城市 16/32 对照](../research/investigation-city_distance_loading_comparison.md)已在相同原始副本与设置下完成两轮 115 秒流程，没有设备丢失。32 视距队列平静后仍约 80 ms/帧；原共享锁等待没有复发，CPU 全量场景组织与动态输入显著增长，GPU 完成区间同时增长但存在背景负载与驻留边界。此结果没有授权恢复其他性能方向，也没有实施新的优化。

随后使用者授权先优化静态组织。[变化驱动快照](../research/experiment-static_chunk_scene_cache.md)已实现并通过自动验证；16 视距的区块组织 CPU 自身耗时为 3.513 → 0.726 ms/帧。候选 32 完整加载并取得平静窗口，但参考 32 在原生 acquire 边界停顿约 98 秒，未取得有效稳态；分析器现明确拒绝漏计的长间隔。实际背景负载也显著变化，整帧和吞吐收益仍有限制，不把旧 80 ms 当作本轮参考。四轮均正常关闭，无设备丢失，没有自动重跑。

剩余验证与定向优化范围：

1. 固定当前源码、实际加载的原生库、模组组合和设置；先记录当前默认双向模式的加载现场。
2. 区分已有区块读取、新区块生成、客户端网格构建和有效几何发布，记录队列积压、真实帧耗时及资源趋势。
3. 追踪数据到达、Java 准入与编译、原生入队与打包、GPU 上传与 BLAS 完成、场景发布；CPU 记录命令不等于 GPU 完成。
4. 静态快照已保留；后续若验证其净收益，需取得负载可比且无长间隔缺失的 32 视距参考。静态快照阶段未同时启动动态输入重写；随后小几何检查和 SBT 精确内容复用见本页新记录。GPU 常驻表、稳定全局索引与 TLAS 增量化仍未实现，SBT 也未改为全局增量场景表。
5. 若后续需要严格前后收益，固定查询合同与诊断配置；已失败的修复前流程不自动重跑，不混用旧成功进程或改变已接受的成像与传光决策。
6. 分别报告加载吞吐、交互延迟、真实帧耗时和内存成本，没有对应指标时明确未测，不扩展为新的架构改造。

本次已有加载、队列平静、逻辑工作量、主队列 GPU 与部分资源统计；尚未测放挖或首个使用新网格的帧。GPU 的纯算法工作、外部抢占、驻留等待及独立区块队列耗时仍需区分；不能只凭接近显存容量或 GPU interval 变长直接认定换页、驱动问题或 shader 退化。空世界高视距成本保持独立待验证。

不减视距、画质、动画频率或 PT 场景几何，不恢复世界后置光栅，不以全局 GPU idle 或关闭功能作为正式修复。自然发生设备丢失时保全证据并停止当前用例，不自动反复重启。
