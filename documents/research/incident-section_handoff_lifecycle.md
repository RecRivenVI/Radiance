# 区段交接的完成、取消与来源退休

2026-10-30，在大型 Sable 结构空确认修复之后，统一检查并完善区段交接的取消、重定位、重载、失败重试及来源空间寿命。配套 K 使用平台 API 12；自动正确性验证通过，未作性能比较，连续人工视觉仍待验收。

## 问题

原生取消和槽位重定位会调用整组成功发布的收尾路径，与 Java 参与者的取消语义不同。多个作用域共享区段时，一个作用域退出可能提前放行其他尚未准备好的作用域。编译异常主要记探针计数并重新排队，默认日志缺少原因，失败也可能被误认为普通加载等待。

现有就绪判断接受当前几何或确认空版本，逻辑本身保留。前一轮修复已让确认空的主世界区段也报告完成；本轮不取消共同发布门槛，不将缺失、失败或过期工作当空。

## 方法

复用实际区段调度、发布与帧退休机制。每个作用域登记自己的区段依赖，共享区段保留其他持有者。取消最后一个持有时，该区段恢复普通版本检查与发布；不把其他作用域记为完成。重定位只丢弃该旧坐标的依赖与暂存结果。

平台区段代际失效后，Java 作用域取消且不向新世界发送旧 token；Sable 重新收集有效来源。持有前更新外部绑定，仅真实属于主世界当前 ViewArea 的对象才能按主世界槽位持有。来源卸载但区段仍被交接持有时，保留最后组合姿态与区段染色，随区段退休，不保留活的来源。

当前编译失败保留旧几何和请求版本，按 250 毫秒至 30 秒退避重试；实际新版本立即准入。重试不调用会重新进入内容变更钩子的 `setDirty`，失败不能保留已准备标记。错误原因与堆栈限频写入日志；持续等待 15 秒后记录来源参与者和缺少的区段版本，此后最多每 30 秒一次，不用超时强行发布。

正式大型结构运行器增加内容完成断言，要求来源交接无积压、成员登记完整、无脏区段且有内容区段数量正确。正常退出、旧几何仍可见及空队列均不能单独作为新版本发布证明。设备丢失同时检查 Java 日志和 Native 控制台，保全证据及实例后停止。
