# 降噪、重建输入与补帧调查

2026-11-02：本轮完成依赖组合升级、已确认输入与生命周期修复，以及小场景自动对照；没有证明普遍帧率提升，尚不代表人工画质验收。

## 问题

反射、透射与随机覆盖的损失可能发生在原始采样、材质引导、降噪或超分阶段，不能仅凭最终模糊归责降噪器。另需确认 SDK 真正执行、RR→SR 切换状态、FG 实际呈现及界面策略。

## 方法

原始候选 `6571eff4…83834`、源码及符号保存在 `versions/1.21.1-neoforge/build/candidates/reconstruction-baseline-20261102/`。最终候选 `bcb7115b…dc4abc` 位于同级 `reconstruction-fgfix-20261102/`，其源码覆盖包基于原始快照，记录精确子模块提交。当前匹配符号位于 Native 构建目录，身份记录在候选清单。

使用项目内 `performance-sources` 的 `r0` 实例，NeoForge＋Radiance＋探针，不带 Extra 或 Voxy。输出 1920×1080，DLSS Balanced 内部 1114×626，四次反弹，静态日照，手动曝光 1，FG 在重建对照时关闭。镜面、单层物理玻璃、水面及独立真实覆盖场景分别观察。双层玻璃另用八次反弹检查，不能将四个界面已耗尽的路径预算误判为降噪黑屏。

运行时断言实际预设、参数和资源包。FRAME_ONLY 记录整帧间隔，TIMED 单独记录 GPU 模块；两种观测开销不同，不混为同一窗口，也不累加重叠 GPU 区间。捕获输入的运行启用额外日志，只用于正确性和图像，不与无捕获基线比较速度。已有基线、SDK 单独升级、输入修正及资源移除分别留证。

证据根目录为 `validations/performance-sources/result/reconstruction-20261102/`。`confirmed-comparison.json` 保留各窗口原值；每案 `cold-text.zip` 和索引保存 CSV、日志、外部负载；`input-captures-*.zip` 保存逐文件 SHA-256 读回校验的原始 AOV。旧名 `coverage` 是物理透射 slime 方块，未算作覆盖验证；后续世界边界走实际 ALPHA_COVERAGE，透射身份为零。

### 输入与历史修复

| 信号 | 实际合同与边界 |
| --- | --- |
| 颜色、曝光 | 重建前是场景线性 HDR，不是显示编码颜色；SDK preExposure／exposureScale 为 1，世界曝光和色调映射在后。SR 未启用额外自动曝光，不伪造重复曝光图 |
| 深度、运动、抖动 | RR 使用 view-space Z，SR／FG 转硬件深度；运动包含相机及对象，以内部像素为单位，SDK 按尺寸缩放。jitter 独立传入，不混进无抖动运动 |
| 法线、粗糙度 | 世界空间着色法线；RR 用 FP16 XYZ＋A 粗糙度，NRD 按其编译编码打包，粗糙度与实际 BRDF 的 GGX 参数一致。SR 本身不接收材质引导 |
| 材质颜色 | RR 必需的漫反射与高光反射率均为线性 UNORM，不是 sRGB。NRD 使用相同去调制／重调制约定，不把入射光烘入材质颜色 |
| 距离与反射运动 | RR 提供首表面反射段距离和相机矩阵，采用官方允许的高光运动向量替代途径；不是总相机路径长度。NRD 的漫反射、高光距离分别归一化；复合透射仍有共享引导限制 |
| 透明、响应信息 | RR 的透明覆盖层、透明前颜色是可选输入，本轮不绑定；没有独立折射专用通道。物理透射和几何随机覆盖保持不同身份，不把可选缺省冒称必需输入缺失 |
| 历史与资源 | 每视图保存历史，重建／切换／尺寸与原点重置时失效。RR／SR 标签有效到 Evaluate，FG 输入有效到 Present；SDK 执行后才推进被接受的重建状态，在途资源不提前覆盖或释放 |

- RR／SR、NRD 与 FG 使用稳定局部原点，先做 double 差再转 float，且使用产生深度、运动的实际 effected camera。重置时前后相机一致，成功执行后才推进历史。CPU 投影检查覆盖接近 ±3000 万坐标、细小平移和旋转；实际游戏远坐标的完整画质尚未专项验收。
- NRD 接收已经无抖动的运动向量，不再额外加相机 jitter；连续每渲染帧转头捕获中，10842 个有效像素都有非零运动，原始与 NRD 运动完全一致。旧的间隔式动作捕获多数恰好落在静止帧，只证明执行，不承担运动输入证据。
- 漫反射使用实际次级命中距离，不再误用相机表面深度。透射有效身份、实际下一段命中距离和概率补偿分别保存，NRD 不再因没有反射距离而抛弃有效透射；归一化参数来自当前 REBLUR 配置。
- RR 材质引导采用视角相关的积分方向反射率，而非直接拿 F0；漫反射颜色排除金属与物理透射。NRD 准备和合成使用同一有界因子，透射／背景复合信号不按玻璃 F0 放大再缩回。
- 首表面发光记录实际增益、来源层及路径权重，从被降噪的续接信号分离后只合成一次。居中的灯具平面捕获中全部 10842 个像素发光非零，最大 14.805；AOV 重组与原始 PT 的平均绝对误差约 0.00376，相比均值 12.42 小于 0.04%，含 FP16 量化。
- 单层玻璃、实际覆盖、双层八反弹与 Advanced 捕获均有限值，透射有效像素有正的归一化距离。连续透射捕获的 AOV 平均绝对误差约 0.000127。

反射和透射仍共享首表面深度、法线、运动与一个高光通道。SDK 没有被虚构成具有独立折射专用输入；本轮没有完整透射 PSR 或独立透射降噪器。均衡采样仍可能比双路径更软、更有噪声和拖影，不能宣布全部解决。

光线锥按世界尺度与路径长度估计纹理 footprint，后续界面延续锥宽；本轮未发现可以证实需要强制最高 mip 的错误，也未强制粗糙度归零或全局锐化。最终细节对比保留原始、降噪和超分图像，但没有建立充分采样的全部光路真值；细小噪声与拖影改善仍须视觉对照。

### 资源与耗时

未使用的 RELAX 与两个 REFERENCE 同时占着 NRD 池；移除后，SDK 描述从 37 张池纹理／29 条管线降至 21 张／14 条。1114×626 下逻辑纹理字节由 115765224 降至 48818280，少约 63.85 MiB／NRD 实例。另移除两张无消费者的透射历史图像、相关描述符、清理与等待。上述是逻辑资源，不包含 Vulkan 对齐、SDK 私有分配或其他场景资源，不能当整卡显存收益。

同内容无捕获日志对照如下；数值为真实渲染帧间隔，单位 ms，前后使用相同 DLSS 内部／输出尺寸：

| --- | --- | --- | --- | --- |
| 双路径镜面 | 5.692→5.624 | 6.146→6.125 | 5.719→5.757 | 6.294→6.412 |
| 双路径玻璃 | 5.850→6.023 | 6.301→6.940 | 5.905→5.965 | 6.317→6.493 |
| 双路径水面 | 5.781→5.968 | 6.299→7.138 | 5.836→5.824 | 6.310→6.254 |
| 均衡镜面 | 4.955→5.317 | 5.554→6.567 | 5.086→5.053 | 5.680→5.597 |
| 均衡玻璃 | 4.760→4.834 | 5.359→5.569 | 4.905→4.912 | 5.379→5.548 |

RR 基本持平。NRD 若干窗口均值和尾部变差，最明显的均衡镜面均值增加 7.3%；不能删除这些窗口，也没有证据将其全归为外部干扰。GPU 玻璃窗口的 NRD 约 0.53 ms，SR 约 0.75→0.785 ms，主队列约 5.569→5.566 ms；不能从局部资源减少推导整帧提速。负载记录无其他 Minecraft，SM 时钟主要 2775～2790 MHz。

因此只补做这两个异常窗口，先按相同脚本恢复整个夹具、清空预览改动与玩家物品，分别运行最终候选和原始包，保留全部样本：双路径玻璃原始→候选为 6.140→6.249 ms，P95 为 6.767→6.688；均衡镜面为 5.718→5.497 ms，P95 为 6.873→6.047。原始包自身也与早先窗口有明显差别，不能将早先 7.3% 全归因代码，也不能用较好的补测覆盖原值。玻璃窗口 NRD GPU 为 0.540→0.632 ms，存在约 0.09 ms 成本增加，具体 SDK／有效信号变化归因未单独闭合。总体结论仍是没有稳定的整帧提速证据，不继续重测寻找正收益。

NRD 两次完整运行进程工作集峰值约 4.33→4.23 GiB、私有提交峰值约 7.48→7.34 GiB；整卡显存峰值 9102→9092 MiB，不是进程显存归因。RR 工作集约 2.60→2.68 GiB、整卡峰值 8842→8843 MiB。场景与 SDK 缓存使整体占用不能直接等同逻辑池差值；本轮短场景不能证明长时间无泄漏。

有限调参中，NRD 半径 100→30 未取得稳定速度收益，默认不改。SR M→K 的单窗 SR GPU 时间约 0.755→0.578 ms，但尚不足以证明动态画质和普遍收益，不强制覆盖个人选择。自动模型交由配套 SDK。

### FG 与 GUI

重复启停并跨 SDR／HDR10 切换时，旧交换链尚存却已卸载其插件，销毁钩子收不到通知；再次加载后 SDK 报“只能有一个交换链”，返回初始化失败。修复为在途工作完成后，先通过仍挂钩的插件销毁旧交换链，再改变插件状态，最后创建新链。不删除同步保护，不重试设备丢失。SDK 日志按真实信息／警告／错误级别输出。

修复候选在 SDR、HDR10 均实际呈现生成帧，SDK 状态成功；重载及 1600×900↔1920×1080 后仍有生成帧。真实 GUI 生产者检查中，HUD、局部反色、背包、无全屏模糊暂停背景继续生成，全屏模糊禁用；退出世界后为 60 真实／0 生成。scRGB 保持关闭。

不限帧的同一玻璃小场景、同一观测配置：FG 关闭约 150～151 真实／0 生成，开启约 107～109 真实加 107～109 生成。FRAME_ONLY 均值 6.640→9.240 ms，P95 7.146→9.906，P99 8.075→10.615。真实帧变慢约 39%，SDK 呈现吞吐增加约 43%。主队列计时约 6.393→7.860 ms；它不包含独立队列的完整生成耗时，不能把差值当成单独 FG GPU pass。此前输出限 60 时约 30 真实加 30 生成，与不限帧数据分开。

PresentMon 1.9.12728.0 在本机以退出码 1 立即结束，无错误说明、无 CSV；没有擅自提升权限。故缺显示端帧间隔与延迟数据。SDK 的实际呈现计数能证明功能生效，不能证明插值像素、运动边缘或响应延迟正确。保存的 FG 图像是实际输入，不是生成帧截屏；HDR10 的真实显示效果仍需 HDR 设备验收。

一次结束检查的控制器漏调 `ClientLevel.disconnect()`，客户端等候仍在运行的内置服务端。线程栈及原版字节码确认是脚本调用顺序，正常请求该项目内服务端停止后退出；该案不标完整成功，前面的完成窗口独立留证。修正控制器后，后续退出检查正常完成。输入捕获还发现并修复一次诊断代码的空弱引用，后续捕获不再崩溃。这些不是设备丢失，也不是用吞异常规避。

## 结论

本轮交付兼容的 SDK 组合、输入一致性、无用资源和 FG 生命周期修复。没有增加反弹、减少几何或强制改变个人质量选择来制造收益，也没有重写介质、HDR 或完整 PT 架构。SER 继续暂停。

`spotlessApply check verifyRelease` 成功，82 项非 GPU CTest 和 29 项 GPU 合同通过；四个重建组合、真实覆盖、多层透射、连续相机运动、资源重载及尺寸切换有项目客户端证据，全程无设备丢失。最终检查日志为 `check-closeout.log`，严格合规结果同录。NRD 尾部波动、共享透射引导、FG 生成像素／显示端间隔／延迟及人工画质验收仍保留边界，不因构建或计数通过而闭合。
