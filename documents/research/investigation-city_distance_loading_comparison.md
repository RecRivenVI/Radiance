# 城市世界 16 与 32 视距加载对照

调查日期：2026-10-15。同一 Newport City 原始快照、同一产品和诊断配置下，两轮各完成 115 秒世界流程、保存和正常关闭，没有设备丢失。32 视距在区块队列平静后仍明显变慢：CPU 的全量场景组织与动态几何输入同时增长，主队列 GPU 完成区间也增长；不再是此前的共享锁等待，不能把全部差距归为着色器、驱动或无条件计算。

## 问题

[前次复测](investigation-chunk_loading_with_gpu_capture.md)只覆盖 16 视距。使用者授权在同一城市副本上比较 16/32 视距，区分加载期间与队列平静后的卡顿，允许其他程序小幅占用 GPU。任一轮真实设备丢失即保全并停止整组，不自动重试；本次不提交、不推送，不改产品渲染语义。

## 方法

两轮分别重新展开命名输入 `newport_city_snapshot`，SHA-256 为 `5e0f1d38256b0e831b10aacad504e866cfe825d0ff508166b374430fdf80e395`，没有重新读取或修改 Prism 世界。准备工具新增显式视距覆盖，逐项核对初始配置，唯一差异为 `renderDistance=16/32`。模拟距离 32、2560×1440、Vanilla PT、SHARC、RR Balanced、FG 关闭、Reflex 2、28 个区块线程、32/32 批次、原始位置与角度及模组组合相同。世界正常模拟，不冻结实体或改变几何。

两轮使用 Java 21.0.11、NeoForge 21.1.259，保留此前相对源 Prism 的 Java/加载器/Zume 差异，不把此对照当成两个环境的 FPS 对照。自动客户端静音，已有伴随组件隔离输入；本轮两组记录均保持焦点，生成帧计数为 0，没有以生成帧 FPS 代替真实帧间隔。

沿用默认轻量取证与 Aftermath 基础采集，不开重型验证；两轮增加相同的有界 JFR profile，最大 128 MiB、栈深 128。逐秒探针新增 UTC 毫秒锚点，按同 JVM 的 UTC 窗口读取 JFR，不相减不同 Java/native 时钟。世界记录为 115 秒，启动预热单独处理，不触发 F3+A，不移动、放挖或切换世界。

产品 Java、bootstrap、原生和 shader 源码相对前次世界复测原始字节不变，新增内容只涉及工具、探针和记录。运行源码快照摘要为 `4f9d1e073d961769a1d54dedb789395c6862231d82ad2553a2ab5090be99643b`。构建、内嵌与实际加载 core DLL 均为 `03c77296594739207b45bb77f0fe827421b174e48f88e7b2063d3b8e8465a558`。参考发行 JAR 为 `cb037eb22297f58b409cae8d5ce3685548f8b52fa5ea45bd5473a53a6b16f6e5`；本次运行使用 GAME/probe 开发输出，不冒充发行安装式启动。两个实际使用的 SPIR-V 多重集合完全一致，各 186 个模块。

## 发现

### 运行、加载与平静窗口

| 项目 | 16 视距 | 32 视距 |

| PID | 89008 | 57020 |
| 世界流程开始，本地时间 | 15:14:06.605 | 15:22:18.666 |
| 世界流程结束，本地时间 | 15:16:01.611 | 15:24:13.722 |
| Java 区段槽位容量 | 26,136 | 101,400 |
| 最终 ready 主世界区段 | 5,241 | 17,427 |
| 首次达到最终 ready 计数，秒 | 11.27 | 83.46 |
| 确认持续平静，秒 | 15.30 | 86.54 |

ready 是发布状态计数，不是首个实际使用新几何的帧。原生输入包含被替代或重复任务，不作为唯一有效区段吞吐。持续四次逐秒采样的 Java/native 队列为空，同时确认种子入队结束、ready 数及服务端读取/生成计数稳定；不能把临时队列空档称为平静。32 视距经历约 1.9 万项重建积压，最终正常排空；静止后卡顿不能再用未完成加载解释。

另取两轮末尾约 20 秒的共同平静范围，逐秒锚点造成实际窗口为 19.87/19.02 秒：平均帧间隔 18.45/80.17 ms，p95 为 21.64/130.12 ms。它支持差距持续存在，不是加载和平静窗口长度不同制造的结果；只有一组顺序对照，背景负载也变化，不把比值写成独占环境的可兑现优化收益。

### 已定位的 CPU 路径

两组全部平静帧的自身耗时，不将 Java 与其内部 native 子阶段重复相加：

| 阶段 | 16 视距 ms/帧 | 32 视距 ms/帧 |
| --- | ---: | ---: |
| 原生区块元数据组织 | 3.91 | 19.81 |
| 原生动态输入 `entity-convert-copy-enqueue` | 2.81 | 13.95 |
| SBT 分配/复制/记录 | 约 0.3 | 2.47 |
| 元数据初始化 | 0.53 | 1.91 |
| Java 实体 renderer 自身分区 | 0.65 | 5.93 |
| Java 方块实体 renderer 自身分区 | 1.67 | 3.60 |

两轮平静时区块元数据缓存均全命中、重建为 0，但 `WorldPrepareContext::render` 仍扫描预留槽位，对有效区段重新组织实例、地址、外观、历史与 SBT 关系。`ChunkSceneMetadata::append` 复用单区段已解析数据，没有消除整场景逐帧组装。因此不能以“缓存已经命中”排除这条 CPU 路径，也不能把缓存问题等同于只复用八个上传缓冲。

末尾共同窗口中，PBR 格式逻辑输入顶点约为 18,833/74,812 个每帧，相关逻辑字节约 2.30/9.13 MiB；动态 BLAS 输入约 200/617 个每帧，TLAS 实例约 5,450/18,053 个每帧。Flywheel 实例均为 5。没有设置实验性的 `radiance.rigidModels`，刚性实例计数均为 0；未擅自启用实验功能制造对比收益。这些是实际工作量，不等于物理 PCIe 传输字节或全部 Java 顶点生成次数。

JFR 的 Java 栈支持进一步分工：动态提交来自 `queueEntitiesBuild` 与 `queueBlockEntitiesRebuild`；`PalettedContainer.get`、生物群系读取还落在客户端方块实体 ticking、`ClientLevel.animateTick/doAnimateTick` 等原版路径。JFR 的主线程保留早期名称 `main`，按 Java 线程身份核对其 Minecraft 调用栈；Java 与 native 两种采样机制分别查看，不混成精确耗时百分比。tick 的 ms/帧也受每帧包含多少 tick 影响，不据此直接推断单 tick 退化。

### 不再是原共享锁；诊断自身也有成本

32 视距加载窗口的两处原共享锁等待最大仅为 0.0012/0.0004 ms，平静后也在微秒量级；不能解释 80 ms 平均帧间隔。32 视距最大的初始帧主要包含 tick 和首次工作，较晚的 160.65 ms 帧则有 66.13 ms 区块元数据阶段，不是此前那条 235 ms 取锁链。

现有驻留盘点每 30 个 profiler 帧执行，位于元数据阶段内。盘点帧平均 wall 为 22.68/95.46 ms，非盘点帧为 18.91/79.33 ms；排除盘点帧后的元数据仍约 3.78/19.19 ms。诊断会加重部分尖峰，但无法独自解释整体差距，不将有插桩的数字冒充无开销产品性能。

JFR 的加载窗口 GC pause 合计约 226/378 ms，平静窗口约 116/40 ms，未出现足以解释持续 80 ms 帧的 GC 停顿。分配采样权重不是完整分配计数。单次真实设备丢失没有发生，不以本轮成功关闭此前 GPU 故障根因或 G3。

### GPU 与资源边界

平静阶段主队列 GPU 完成区间均值约 16.00/64.96 ms，世界模块区间约 15.40/61.61 ms；动态转换、BLAS 和 TLAS 的已插桩区间也增长。父子区间重叠，不相加，不把这些完成区间直接称为纯 shader 活跃时间。独立区块队列仍只有包含排队和轮询的批次完成墙钟，缺少纯 GPU 分段。

应用按 buffer 对象去重统计的已发布区块资源约 2.22/6.75 GiB，不覆盖 SDK、整进程、全部临时和在途分配。整卡 NVML 峰值为 12,731/15,276 MiB；32 视距资源余量更小，但没有预算/逐进程驻留与抢占证据，不能断言已经发生显存换页。系统 CPU 平均约 32%/45%，仍有约 40 GiB 以上可用物理内存；其他程序存在且负载变化，GPU 抢占、驻留等待及环境影响不能由此排除。

`buffer.persistent-records` 为约 36.6 万/142.0 万，随槽位容量增长。源码中的该表包含尚未初始化 GPU storage 的占位项，不能把它写成同等数量的 GPU 分配或显存泄漏；正常上传走 pending 集合，参考全表扫描开关本轮未启用。

### 验证、工具纠正与证据

`spotlessApply check verifyRelease verifyCompliance --strict` 通过，严格合规失败 0、警告 0；输入与关闭分析回归 9/9，非 GPU CTest 64/64，probe 与 bootstrap 测试通过，其余已有 Java 测试包含有效缓存结果。没有改产品或 shader，因此没有重跑不相关 GPU 合同测试。两轮实际运行的保存、场景释放、正常设备关闭、SDK disable 与退出码 0 均有证据；帧输出、原生事件与容量丢弃为 0，没有转储或同期 Windows GPU 事件。

首次离线 `jfr print --json` 反复展开共享元数据，派生文件膨胀至约 19.4 GB；已停止两个只属于该导出的进程，未操作任何游戏。改用限制 Java 堆的 `RecordingFile` 逐事件读取，只输出所需调用与统计。原始 JFR 约 15.0/14.4 MB 保持完整；确认 D 盘回收站策略和配额足够后，将无用的截断派生 JSON 送入 Windows 回收站，没有清空回收站或删除原始记录。

## 结论

已把问题分成两部分：32 视距加载实际处理更多既有区块，加载时间与每帧成本均增长；队列平静后，全量场景元数据和更大的动态输入仍持续占据 CPU，GPU 完成区间同时变长。调度受帧推进影响是源码已知事实，但其对本次吞吐的独立贡献尚无解耦实验，不能据此指定为唯一瓶颈。无需先降低画质、删除相机外几何或恢复后置世界光栅来解释现象。

后续技术优先级是先减少已测量的静态场景重复组织与动态模型重复生产；稳定身份、时序、完整场景及退休约束仍须保留。GPU 部分进一步归因需要区分算法工作、抢占与驻留，不能凭这组背景负载不固定的结果指定驱动、硬件或单面规则为根因。城市结果也不能自动解释尚未复测的空世界高视距固定成本。

本轮只补强诊断并完成对照，没有实施性能优化、部署 Prism、提交或推送。两次短时无故障不是长期稳定性证明。
