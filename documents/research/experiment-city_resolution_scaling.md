# 城市分辨率敏感性与 CPU／GPU 限制

2026-10-18，按使用者授权在同一城市副本采集 720p、1080p、1440p、2160p，判断 GPU 渲染是否已成为瓶颈之一。结果支持低分辨率主要受 CPU 侧限制，而 2160p 已受 GPU 执行／等待限制并伴随 SDK 显存预算告警；后者不能作为纯着色器算力或硬件理论上限。

## 问题

沿用[GPU 帧预算盘点](investigation-city_gpu_budget.md)的产物和计时设施，仅改变测试视口，不降低质量、视距、几何参与或动画频率。帧间隔、渲染线程 CPU 时间、GPU 完成区间和生成帧率分别报告。此次不是性能优化前后比较。

## 方法

### 固定输入与实际执行

- Intel Core i7-14700K、RTX 4080 SUPER、16,376 MiB、驱动 617.14。没有修改频率、驱动、TDR 或系统计数器权限。
- 项目内 `performance-scene_diagnosis`，32 视距／32 模拟距离、Vanilla PT、RR Balanced、SHARC 开启、Reflex 2、FG 关闭、区块发光收集关闭，VSync 关闭、上限 260，静音及相同模组组合。
- 每次启动前恢复同一已逐文件校验的城市 ZIP，SHA-256 为 `40F41782F1A065500B321C6A588B925BD5425233D741E014EBC7F8DC833B3B02`；四份图形设置逐字节恢复，只有本次启动参数改变窗口尺寸。
- 相机固定为 `95.784462690,141.607489199,12.897247229`，yaw／pitch 为 `53.53503,32.74906`；全部正式帧为同一维度、ChatScreen、无雨雪雷暴，生成帧计数为 0。存档恢复不保证加载耗时、逐 tick 动画及随机输入完全相同。
- 至少预热 60 秒且 Java／原生构建队列连续平静 10 秒后采集 60 秒，随后资源重载、保存与正常关闭，600 秒总期限。正式采样期间区块排队观测均为 0，静态重建偶有来源更新，未冻结世界。
- 使用既有防激活和输入屏蔽 companion。其 `correctnessOnly=true`，所以 companion 的 `frames=0/worldEntered=false` 表示没有使用其便携采样器，不表示未进入世界；以城市日志与本项 profile 判读。profile 的 `focused=true` 是游戏缓存状态，不是逐帧操作系统焦点测量。
- 默认本地 Aftermath／轻量取证保留，不开启重型验证或 Nsight；其他项目客户端仍存在，不操作它们。整卡遥测不是本进程独占测量。

### 尺寸门禁与首次失败

最初的三个低分辨率窗口使用普通窗口；2160p 请求实际只得到 `3840×2130`。该次完整流程保留为 `res2160`，不能充当标准 2160p。随后探针尝试在菜单中直接调整，5 秒仍不满足尺寸，`res2160b` 在进入世界前停止，未采样；两次都没有设备丢失。

为取得标准尺寸，只在 `CityFrameComparisonProbe` 增加显式 `radiance.audit.cityWidth/cityHeight/cityBorderless` 选项：默认不启用；仅显式城市对照在标题界面调整 GLFW 窗口，并核对实际 framebuffer 后才打开世界。不是修改生产渲染、全屏模式或驱动。正式四档全部采用相同的无边框窗口方式，最终选择 `res720b`、`res1080b`、`res1440b`、`res2160c`，不把前面有边框的样本混入主表。

本轮共 9 次客户端启动，其中 8 次完整世界流程，7 个满足标准尺寸的窗口；另一个完整窗口尺寸不符，一个菜单门禁失败。没有自动故障重试；在发现显存预算告警后没有再运行 2160p。

### 证据与复现

证据根为 `validations/performance-scene_diagnosis/result/resolution-sweep-20261018/`。每个 case 的 `receipt.json` 给出完整命令、起止时间与原始 profile 路径，`analysis.json` 给出 raw CSV 哈希与分布，`gpu.csv` 为每秒整卡遥测，`client-evidence.zip` 与索引保存关闭和配置证据。`experiment-tools.zip` 为早期工具，`experiment-tools-v2.zip` 为最终控制方式，ZIP 均逐条读回校验 SHA-256。

Gradle init script 仅改变本次 RunModel 的参数；没有修改模板、`local.toml`、实例公共分辨率或生成的参数文件。命令形式如下，须先由已归档工具恢复同一夹具，并使用未用过的 label：

```powershell
.\gradlew.bat :version:1.21.1-neoforge:runValidationPerformanceSceneDiagnosisClient -PcityComparisonLabel=resolution-new-case -PsweepWidth=1920 -PsweepHeight=1080 -I D:/Workspaces/Scratches/RadianceSemanticsAudit/resolution-sweep.init.gradle -x :native_renderer:installNative --console=plain
```

GPU 时间戳沿用既有 fence 后的非阻塞读回；缺失在途尾部不补零，分位数采用 nearest rank。父子阶段重叠，CPU、GPU、模块和 pass 不能相加。`pt-pass/world` 包含参数／屏障及追踪，GPU 区间也可能含依赖等待、调度或驻留开销，不等于纯 SM／RT 核执行时间。

### GPU 分段

单位 ms，为各自有效样本的均值；表中存在嵌套关系。

| 区间 | 720p | 1080p | 1440p | 2160p |
| --- | ---: | ---: | ---: | ---: |
| 主队列整体 | 9.336 | 19.279 | 25.139 | 132.017 |
| 世界 PT pass | 5.428 | 13.627 | 19.194 | 85.531 |
| DLSS 模块 | 0.749 | 1.685 | 2.325 | 9.784 |
| 实体 GPU 转换 | 0.042 | 0.043 | 0.041 | 8.549 |
| 实体 BLAS | 0.983 | 1.179 | 0.950 | 10.221 |
| TLAS | 0.265 | 0.292 | 0.250 | 5.639 |
| SHARC 更新 | 0.181 | 0.277 | 0.365 | 1.035 |
| SHARC 解析 | 0.133 | 0.175 | 0.121 | 0.280 |

720p～1440p 的像素相关 GPU 成本明显增长，但整帧均值仍接近 40～42 ms，渲染线程 CPU 时间也接近整帧。低分辨率主要受 CPU 侧限制，不支持“只降低 PT 像素就能达到 60 FPS”。GPU 时间较短也不表示其未来无需优化：当前 1440p GPU 区间已超过 60 FPS 的 16.667 ms 帧预算。

2160p 的主队列完成区间约等于整帧，CPU 执行时间明显小于整帧，同时全部 GPU 子阶段广泛变慢。相同几何输入下，实体转换与 AS 区间也大幅增加，不能把它们全部解释成几何工作量增加；GPU 侧等待、驻留与调度需要后续独立证据。

### 显存预算与运行间波动

2160p 日志在采样前后反复出现 Streamline 的 `Exceeded VRAM budget` 警告，完整流程计 358 条，明确提示可能出现卡顿；不是本项目捕获的 GPU crash dump，也不等于 `VK_ERROR_DEVICE_LOST`。第一份尺寸不符的近 4K 窗口也有预算告警，不能用它推导精确 2160p 成本。

2160p 单点 Windows GPU Process Memory 为 dedicated 12,603,572,224 bytes、shared 1,596,497,920 bytes、total committed 14,166,712,320 bytes；1440p 辅助旧窗口另留单点。它们不是驻留／换页时间线，不能仅由 shared 非零宣称已证明分页原因。进入世界前的窗口校正是否增加资源驻留，也没有单独消融；不将极端 2160p 数值当作纯像素算力曲线。

| 档位 | 整卡利用率均值 % | 图形频率范围 MHz | 整卡显存均值／峰值 MiB |
| --- | ---: | --- | ---: |
| 720p | 30.00 | 2625～2790 | 13541 / 13936 |
| 1080p | 52.90 | 2700～2790 | 13762 / 14126 |
| 1440p | 62.87 | 2790～2790 | 14827 / 15127 |
| 2160p | 99.78 | 2790～2790 | 15757 / 15982 |

整卡总显存为 16,376 MiB。其他程序仍使用 GPU，未取得进程级占用时间线或可用的硬件计数器；WDDM 预算与整卡物理剩余容量不能互相替代。此次没有关闭其他程序、调低画质或更改 SDK 路径来隐藏预算问题。

早期有边框 1080p 为 36.328 ms，后续无边框为 41.860 ms，差约 15.2%；两边 GPU 分别为 18.038／19.279 ms，均短于整帧。时间、窗口方式和外部负载共同变化，没有把差值归因为边框或某项优化。早期 720p／1440p 均约 34 ms，最终同窗口方式下约 40～42 ms，也表明不能报告严格的小幅收益。

## 结论

1. GPU 渲染已经是当前场景的限制之一；低分辨率当前主要仍受 CPU 侧限制，两者需要分开优化。
2. 2160p 已呈 GPU 执行／等待主导，并出现明确显存预算告警，不能由 132.605 ms 推导本机纯 PT 理论帧率上限；需要先分离预算／驻留和渲染计算成本。
3. GPU 优先关注世界 PT 及其遍历、材质、透明路径；CPU 继续按动态输入生产者归因推进。此报告没有授权或实施下一项算法优化，也没有以减少几何、冻结动画、世界后置光栅或降质换帧率。
4. 本轮只补测试视口门禁与证据；没有投放 Prism、修改外部实例、暂存、提交或推送。设备丢失根因、完整稳定性和公开二进制许可结论均保持原边界。
