# 城市性能基准配置更正与重测

2026-10-29，使用者提供 Prism 的 1440p、约 51 FPS 截图后，复核发现上一轮城市夹具遗留了 128 次最大反弹和前景／背景混合。此前将其描述为四次反弹、随机覆盖是核验错误；本记录更正解释，并以当前 Prism 配置重新建立基准，不将配置变化当作产品优化收益。

## 问题

[上一轮调查](investigation-renderer_performance.md)的帧时间是其实际运行配置的观测值，但不能代表使用者正常配置，不能据此判断普通游玩的 GPU 瓶颈或帧率上限。关闭完整诊断的旧对照，也只能说明诊断不是那套异常配置的主要成本。

`radiance/options.properties` 中遗留的 `rayBounces=4` 不是当前 PT 的权威参数。冻结 E 源码中的 `Pipeline.getModuleAttributes` 会读取算法包同名 `.zip.txt`，本轮复核确认旧夹具在该文件中保存 `num_ray_bounces=128` 和 `coverage_mode.blend`，探针没有覆盖。默认值不能代替已载入的算法参数。最大 128 次也不表示每条路径都恰好执行 128 次。

## 方法

### 输入和差异

- 只读核对当前 Prism：Core 和 Extra 哈希与原性能配套一致；Voxy 已禁用，FG 关闭，32 视距和 32 模拟距离，DLSS Balanced，四次反弹、随机覆盖。
- 将 options、管线和算法参数及两份已启用 SPBR 资源包冻结为 `prism_city_baseline_20261029`。输入版本、哈希与本机路径分别登记在 `inputs.toml`、`local.toml`，来源与逐文件读回证明保留在快照旁的 JSON。没有写入 Prism。
- 使用同一纯原版城市冻结 ZIP、同一保存相机和同一 Core E／Extra D。自动副本只覆盖输出尺寸、静音、窗口和失焦暂停；内存按当前 Prism 继承值使用最大 16 GiB、初始 512 MiB。没有修改 EULA、默认画质或产品代码。
- 旧夹具的批次大小／总批次为 8，新快照沿用 Prism 的 32；堆上限也由执行器默认 8 GiB 对齐到 16 GiB，并加入两份 SPBR。新旧是完整配置更正，不是只改变反弹次数的单变量实验，不能把全部差异归到某一个参数。
- 测试只装 Core、Extra 和探针，没有 Voxy 或其他兼容模组。项目内加载器为 21.1.259，Prism 为 21.1.265；截图视角也比冻结相机更平。因此本轮适合建立可复测基准，不能视为完整 Prism 组合的逐像素对照。

### 生效参数核验

新探针在计时开始前读取已经载入的 `Pipeline.INSTANCE` 模块参数及实际资源包顺序，与冻结输入逐项比较，不重新加载或修改参数。四次反弹、随机覆盖、DLSS 管线和资源包不一致即拒绝接受样本；不再只检查普通选项。

测试保存 `expected-rendering.json` 与 `effective-*.json`，同时继续核对实际 DLL、视口、相机、完整区段队列平静、数据缺失和正常保存退出。截图读回和重载放在正式计时窗口外。FRAME_ONLY 用于整帧，TIMED 用于分段，两者分开比较；父子计时不相加。

本轮实际探针为 `components/render_diagnostics/build/renderer-campaign-20261029/probe-prism-retest-b.jar`，SHA-256 为 `c962214e28c020ddf13accc0978cd6eba3c88aec058e3d555364067a79255237`。51 项探针测试和 23 项工具回归通过，包内确有生效参数检查类。首次构建命令排除组合组件 JAR 后，关联的目标任务未实际执行，已在启动前通过检查 JAR 发现并修正；第一份副本没有运行。

## 发现

### 正常配置基准

| 输出尺寸 | FRAME_ONLY 平均 | p95 | p99 | 最长 | 真实 FPS | 渲染线程 CPU 活跃均值 | 主队列 GPU 均值 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1920×1080 | 24.38 ms | 27.37 ms | 29.74 ms | 45.66 ms | 41.02 | 24.34 ms | 11.99 ms |
| 2560×1440 | 25.32 ms | 29.45 ms | 32.34 ms | 43.11 ms | 39.49 | 24.94 ms | 22.04 ms |

两个有效窗口实际载入四次反弹、随机覆盖及两份 SPBR 包，FG 均关闭，无设备丢失，正常重载保存。FPS 由均值帧间隔换算，不包含补帧。窗口不是与使用者截图同一时刻、同一角度的配对，不能把约 39.5 和截图约 51 的差值直接归为探针或渲染器回退。

1080p TIMED 的世界 PT 约 8.81 ms；1440p 约 14.90 ms。两侧的整帧仍相近，且 CPU 活跃接近整帧墙时，当前点位应优先关注 CPU 来源与提交，1440p GPU 也已接近帧预算。Windows 线程 CPU 时钟为 15.625 ms 量化，使用窗口均值，不作单帧精细减法。

1080p TIMED 中，提交／呈现约 7.83 ms、来源状态 2.62 ms、实例打包 2.12 ms、实体主体 1.90 ms、方块实体 1.89 ms、实体输出 1.81 ms、部件绑定 1.43 ms、tick 1.61 ms；Native 内部静态追加约 1.60 ms、TLAS 命令组织 1.32 ms、内容元数据选择 1.11 ms。Native 内部项包含在 Java 提交中，不能再次加到整帧上。TIMED 相比 FRAME_ONLY 自身也有观察开销，不能用它代替真实 FPS。

### 诊断对照与 CPU 归因

同一 1080p 画面关闭完整审计 Mixin、Native 采集器及 Aftermath，仅保留自动控制、输入隔离和最小计时，平均 **24.71 ms**、p95 **28.42 ms**，与 FRAME_ONLY 的 24.38 ms 接近。共同的 CPU 故障面包屑和输入控制引导仍存在，不称为完全无诊断；这次对照也覆盖正常配置下的 CPU 受限情形。

独立归因序列的两个 TIMED 窗口分别为 30.53／26.10 ms，中间 JFR CPU_SAMPLES 为 39.71 ms，最长约 439.59 ms。后者显著受观察影响，不纳入正式 FPS。JFR 的 116 个渲染线程样本中，client tick 35、实体 29、Native 提交 29、Native acquire 6；样本不是墙时比例，且 31 条栈达到记录深度限制。以正常 TIMED 的约 7.85 ms 提交、2.63 ms 来源状态、2.11 ms 打包及约 0.72 ms acquire 作为细分依据，不能继续沿用旧的约 125 ms GPU fence 等待排序。

当前窗口每帧选择约 4,134 个持久实例、约 217 个发生参数变化；Java 实际生成 816 个 PBR 顶点、104,448 个逻辑字节，稳定引用约 18 万个顶点。持久复用真实生效，来源状态整理、选择／打包和 Native 场景组织仍有工作。SBT 每帧约四次请求，约 3.90 次复用、0.10 次冷上传；本场景不宜再次把全量顶点生成或全量 SBT 上传当作主因。

### 正常配置的生命周期和内存

生命周期用例为 `lifecycle1080-r32-1080-20261029-184012`，使用同一 B 探针和设置，另开 1 Hz 普查、Native 分配跟踪、WDDM 与 NMT，不能当作轻量 FPS 基准。初次进入后的队列平静约 153 秒；重进约 54 秒。第二次包含第一次保存的新生成内容，不能把差异全部算成渲染缓存收益，也不与旧夹具批次 8 的时间直接比较。

实际飞行 180.6 秒、七次往返转向；返回原相机后创建 64 个盔甲架和 64 个无 AI 僵尸，静止、移动、移除后观察，再退出重进，均正常结束。移动和移除后的 p95 约 46 ms，但这是带普查的连续压力序列，不能由此独立证明实体导致多少用户可见卡顿。阶段边界来自 1 Hz 记录，进出世界附近的长帧不归罪于实体删除。

Windows 本进程 GPU Dedicated 计数从初次静止约 11.57 GiB，移动后约 12.55 GiB，回菜单分别降至约 6.33／6.18 GiB；Shared 峰值约 2.11 GiB，不能直接等同于驱动换页。私有提交峰值约 23.19 GiB，物理工作集峰值约 9.41 GiB；Java 实际堆在多数观察阶段约 2.7～3.2 GiB，没有强制 GC。

两次退出后的 VMA 总块／有效分配分别是 `6,969,737,216 / 1,860,725,488` 字节和 `6,701,301,760 / 1,863,772,912` 字节。最后有效量约 1.74 GiB，块仍约 6.24 GiB，块内约 4.50 GiB 未使用；有效内容释放和分配块驻留应分开判断。本次仍支持分配块碎片值得处理，不支持无限活资源泄漏已复现，也没有证明任意时长都无泄漏。

另发现长期帧采集原有 20,000 帧保护先于生命周期结束触发，最后约 52 秒未覆盖逐帧记录，包含部分重进静止和第二次菜单；1 Hz 内存、WDDM、NMT 与五份 VMA 释放图完整。覆盖缺口已明确写入 `frameCoverage`，不将最后菜单写成有完整帧时间。后续探针给生命周期单独设置 60,000 帧有界上限，普通采集仍为 20,000，原始输出的 128 MiB 保护不变。本次没有为补这一段重复整场运行。

### 证据与保留

数据位于 `validations/performance-sources/result/retest-20261029/`，1080p 和 1440p 分别为 `normal1080-r32-1080-20261029-175311`、`normal1440-r32-1440-20261029-181220`。分析、设置核验和截图保持原文件，已完成窗口的大型 CSV／追踪文本在各自 `evidence-raw.zip`，索引和 SHA-256 逐条读回验证后才回收原件。

为满足既有容量，回收约 785 MB 可再生缓存和重复 Native 载荷，逐文件与保留的构建 JAR 比较；没有删除冻结候选或其 PDB。旧 `performance-vanilla/result` 的约 37.45 MB 文本无损归档为 `cold-text-20261029.zip`，原路径映射在同名索引，修改了 `experiment-vanilla_renderer_replacement.md` 的归档引用。预算不足的 1440p／控制组预检没有启动客户端，不属于设备丢失或自动故障重试。

夹具还出现 53 次旧地图数据的 dimension 加载警告，最后一次均早于正式静止窗口，没有在此任务修改地图数据或静默删除对象。这是与实际 Prism 存档内容等价性的额外边界，不能由本次截图证明所有地图画面相同；不妨碍固定夹具内部的配置重测。

## 结论

本轮纠正了测试基准，尚未实施产品优化。旧约 170／289 ms 不应继续当作正常 1080p／1440p 的性能依据；其内存分配块图等独立证据仍保留，但占用和优先级也需按新的实际运行口径区分。

最小观察者、CPU 归因与正常配置的内存生命周期已完成。1080p 的下一优先项应是来源及场景提交中的真实 CPU 重复工作；1440p 还要考虑约 22 ms 的 GPU 主队列。显存块碎片是独立的资源优化候选，不宜因 CPU 已受限而把更多必要 GPU 数据搬回主机、增加传输和等待。静态 BLAS 构建策略仍可后续单独评估，但不应继续由异常配置下的 PT 耗时决定最高优先级。

没有产品改动、设备丢失、提交、推送或新投放，不承诺真实 60 FPS，不以配置更正充当产品优化收益。没有重复 4K 压力运行；两档分辨率已能区分当前 CPU 与 GPU 的限制，自动数据不替代用户视觉验收。
