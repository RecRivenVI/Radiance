# 城市加载完成后的 32 视距现场诊断

2026-10-18，使用者复测旧 8 视距卡顿场景，认为与实体数量有关，并通知当前城市 32 视距已加载完毕、可以捕获。本次取得一个 60 秒固定相机窗口，区分持续 CPU 成本和周期性长帧；未实施产品修复或优化前后 A/B。

## 问题

判断城市在加载基本结束后为什么仍卡顿，以及它是否与此前被称为“多光源”的现场存在共同路径。8 视距的实体数量判断属于使用者观察，没有受控增减实体对照，不能直接当作唯一根因。

前次轮廓现场、半透明与世界底部的独立结论见[三个场景归因](investigation-three_scene_paths.md)。这里不把不同世界、配置、候选或场景名称拼成一次对照。

## 方法

在仍运行的项目内客户端 PID 72072 请求 `city-r32-loaded`，使用[场景诊断入口](../../validations/performance-scene_diagnosis/validation.md)。北京时间约 00:50:45～00:51:45，共 1,065 个真实渲染帧；用户操作后的相机全程固定为 `(95.784462690, 141.607489199, 12.897247229)`，yaw `-666.46497`、pitch `32.74906`。记录是 Java 帧尾观察，不是 GPU uniform 读回。

实际窗口为 1920×1080、32 视距，全部失焦、`ChatScreen`，世界仍运行；生成帧计数全为 0。来源设置保留 32 模拟距离、Vanilla PT、RR Balanced、Reflex 2、vsync 关闭和普通覆盖混合，未在本轮改变质量、相机或世界。反弹数不能只取旧 Options 字段：该字段为 4，但 pack 配置的 `num_ray_bounces` 为 128；本轮未读回最终执行参数，不宣称已经证明实际为 4。配置内容身份以文件哈希固定，来源夹具与产物链见[城市准备](../project/plan-scene_performance.md#2026-10-18-城市综合诊断准备)。

实际加载 core SHA-256 为 `81A42375A51E0843FA41E6C5B55D830FB07C939974D1511BC8295EEDC990533A`，与构建和 JAR 内嵌一致。新增逐 pass、拓扑及相机诊断已在真实窗口产出。没有失败帧、writer/native/output-cap 丢弃或本次设备丢失；不由此推导长期稳定性或首次故障根因。

原始证据为 `validations/performance-scene_diagnosis/result/profiles/2026-10-17T16-50-45.732024200Z-pid72072/` 的帧表、分段、计数、报告和 JFR。目录名使用 UTC，文中时间使用 Asia/Shanghai。外部分析、请求日志、板卡遥测和加载身份位于 `D:/Workspaces/Scratches/RadianceSemanticsAudit/`：`city-r32-loaded-analysis-v2.json`、`city-r32-profile-request.log`、`city-r32-board-process-samples.json`、`city-scene-loaded-modules.json`。

40 秒 JFR 晚于主窗口约 38 秒才开始，主分析只使用近似时间交集中的样本。14 份遥测也只有部分重叠；板卡显存／利用率包含其他进程。原始 JFR 保留，打印的 JSON 只在内存解析，没有生成重复的大导出。

百分位使用与探针一致的 nearest-rank：排序后取 `ceil(p*n)-1`。初稿采用线性插值且未过滤 JFR 时间交集，保留为 `city-r32-loaded-analysis.json`；最终数值以 v2 为准。帧与 JFR 的关联使用 metadata 绝对时间加逐帧间隔，只是近似定位，不宣称跨时钟严格校准。

## 发现

### 持续成本主要在 CPU，不是大量后台区块仍在编译

| 指标 | 本次窗口 |
| --- | ---: |
| 真实帧起点间隔均值 | 56.358 ms，约 17.74 FPS |
| 起点间隔 p50／p95／p99 | 50.658／65.939／134.088 ms |
| 最长起点间隔 | 579.084 ms |
| 渲染线程 CPU 均值 | 55.238 ms |
| 主队列 GPU 完成区间均值 | 16.233 ms |
| 其中 world PT pass | 11.337 ms |
| GPU 实际返回帧 | 1,063，缺少尾部不补零 |

渲染线程 CPU 接近墙钟，主队列 GPU 明显更短，支持本窗口主要由 CPU 供给限制。CPU 时间有 Windows 时钟量化，GPU 区间和 CPU 重叠；不能相减后将差值全部指定为可删除工作。

35 次驻留观测的 queued/inflight 均为 0，静态快照重建与 cache-build 均为 0，仍有 2 次区段编译、共约 15.94 ms 的后台时间。应称基本平静，不能写成世界完全没有更新。静态记录 17,705、几何 31,559，TLAS 18,482 个实例保持固定；实例数不等于逻辑实体数。

### 动态生产、入队与场景准备分别有成本

| CPU 分段 | 每记录帧自身耗时 |
| --- | ---: |
| Java 几何 marshal | 13.472 ms |
| Java 实体绘制自身 | 7.425 ms |
| Java 方块实体绘制自身 | 5.661 ms |
| native 动态转换／复制／入队自身 | 12.120 ms |
| native 静态快照追加／实例组织 | 2.591 ms |
| native BLAS 记录阶段自身 | 2.220 ms |
| native SBT 分配／复制／记录 | 1.884 ms |
| native 已展开几何拓扑 | 1.106 ms |
| native 表面层合成 | 0.194 ms |

native 行包含在 Java 调用中，表内也并非所有行都是互斥总分区，不能将整表相加。`BLAS 记录` 是 CPU 录制阶段，不是 GPU 构建耗时；相应 GPU 动态 BLAS 约 0.962 ms，GPU 转换约 0.042 ms。

每帧 PBR 来源约 75,623 个顶点、9.68 MB 逻辑来源字节；其中约 55,499 个顶点走 GPU 延迟转换，直接来源约 7.10 MB。动态 BLAS 输入 609，普通持久模型实例计数为 0。其他上传／输出计数存在重叠，不能加成总 PCIe 传输；零普通持久实例也不表示 Flywheel 常驻路径不存在。

本窗口没有捕获到此前大量 `captured-lines` 来源计数。因此，两处现场的共同点是动态输入 CPU 链路较重，具体热点并不相同：旧发光轮廓现场拓扑协调很重；当前城市的主要宽段是 marshal 和入队。不能用旧轮廓数据解释这里全部 12.120 ms。

该入队路径在 GPU 快路之前仍执行 `rawHasTwinQuads`，调用 `hasReversePolygonPair` 扫描位置和配对资格；这部分没有独立分段，属于宽段内需要确认的候选。不能为省时间直接关闭配对保护，也不能宣称已经测出它独占全部入队成本。

### 半秒长帧出现字体所有者登记与弱引用清理热点

6 个最慢 runTick 约 490～579 ms，主要增长在实体或方块实体自身阶段。JFR 覆盖到的其中两次长帧内，取得如下执行栈：

- frame 1012，约 551 ms：`FontAtlasLifecycle.register → BufferSource` 构造注入 → `StorageVertexConsumerProvider` 构造；同一帧另一样本为 `WeakHashMap.expungeStaleEntries → ReferenceQueue.poll`。
- frame 838，约 515 ms：采到 `WeakHashMap.expungeStaleEntries → ReferenceQueue.poll`。

源码确认 `FontBatchBufferSourceMixins` 在每个 `BufferSource` 构造完成时登记到全局弱键表，包括每帧为实体／BER 创建的 `StorageVertexConsumerProvider`。后者覆盖 `getBuffer`、使用自己的 `pending`，不是每个对象都持有原版 `startedBuilders` 字形批次。GC 后，后续普通登记可能同时承担积压弱引用清理。

这已经是“F3+T 字体生命周期保护扩大到高频无关构造路径”的直接代码与运行热点证据；尚未做修复对照，不能将所有尖峰和所有持续低帧率全部归给这一张表。修复方向应是按实际字形批次所有权登记／退订，并保留页退休前清理旧批次的保障，不能删除字体生命周期保护或吞掉异常。

JFR 交集内观测到约 46～51 ms 的 young GC 停顿，以及约 14.74 ms 的 remark。`G1Old` 约 369 ms 包含并发阶段，不能将整个 collection duration 当作停顿，更不能据此宣称半秒长帧就是一次半秒 GC。

### 开销和未覆盖范围

六个 10 秒子窗口的帧间隔均值约 60.04、64.63、55.27、52.83、54.03、53.16 ms。前段有额外波动，全窗口及原始长帧保留，不择取末段伪装整体改善。诊断、首次 JIT、JFR 启动及其他进程的影响未独立量化。

这一窗口不是“实体数量高低”的受控 A/B，也未测 16 视距或移动／加载阶段。按使用者要求不自动改变实体、移走相机、重新加载或开始其他样本；客户端留给使用者操作，不复制正在写入的城市存档。

## 结论

本次已完成获授权的 32 视距加载后现场捕获，证据支持 CPU 持续供给成本和字体弱引用登记相关长帧需要分别处理。与旧轮廓现场存在动态输入链路上的交集，但不能合并为“光源采样”根因，也没有证明高视距的全部影响都来自实体数量。

下一项最小修复候选是收窄字体批次登记的实际所有权，保留 F3+T、字体页代际及关闭保护；持续成本则优先细分 native 入队中的配对资格扫描与数据组织。尚未修改产品、重建、投放、暂存、提交或推送，不宣称已经提速。
