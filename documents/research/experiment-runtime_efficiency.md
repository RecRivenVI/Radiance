# 城市 CPU 提交与资源驻留收敛

2026-10-29，本轮在正常游玩配置下继续调查 CPU、GPU、内存及显存。以下记录区分整帧、嵌套范围、分配量、实际驻留及人工体验；本轮不带 Voxy。当前候选为 I，站立与移动对照分开解释，不将测试诊断的省时全部挪为普通实例收益。

## 问题

正常配置下，1080p 城市主要受 CPU 来源准备和 Native 提交限制，1440p 的 GPU 工作也接近关键路径。退出世界后，有效资源已释放很多，但少量长期资源仍固定着大块内存。旧的 128 次反弹、前后景混合样本不适用于当前游玩配置，口径修正见[基准复测](investigation-city_baseline_retest.md)。

本轮目标是减少已确认的重复工作和无效驻留，保留完整几何、相机精度、材质、历史及在途资源保护；没有建设新的 GPU 场景数据库或改写第三方来源。

## 方法

固定城市夹具 SHA-256 为 `832a650f7dc6ecba23822d49d767fd0a609f00b3faff6df3f657e2cced0f723e`，Prism 配置输入为 `prism_city_baseline_20261029`，SHA-256 为 `97cb78a16363a7e7818317d49f982ccecd916a5b9d25f5234e2539f46793e0e7`。实际加载参数核验为 Vanilla PT、四次反弹、随机覆盖、DLSS Balanced、关闭 FG、32 渲染及模拟视距，堆上限 16 GiB、初始 512 MiB。原配置 `collectChunkEmission=false`，未擅自切换；本轮不据此评价 Advanced 多光源、远景代理或未执行的灯光收集成本。自动实例静音，不操作 Prism。

本机为 RTX 4080 SUPER 16 GiB，驱动 621.01。基线 Core E 为 `ca9eaf37…`，Extra D 为 `1093201e…`；当前候选 Core I 为 `8407f036…`。正式对照共用 C 探针 `f9c9ef83…`。完整哈希、DLL/PDB 配对与源码快照登记在 `D:/Workspaces/Artifacts/Radiance/performance-runtime-20261029/` 的清单。源码对应未提交工作区，不以 HEAD 代替源码身份。

`runtime-final-20261029` 的 I 功能重载正常结束，字体违规为零，但主机收尾错误地要求了仅性能窗口生成的配置检查点。该次的 STOP 与原始证据保留，不计入性能基线。运行器已将无性能窗口的 `functional` 与性能基线门槛分开；所有正式计时仍必须有有效设置检查点。没有把这一主机检查失败记为 GPU 崩溃或自动重试设备丢失。

静止与五赫兹、振幅四方块的固定相机移动分别比较。FRAME_ONLY 用于整帧；TIMED 只解释分段。另以 G 探索、以最终 I 核验三分钟实际飞行、128 个实体创建和运动、移除、两次退出及重进，采集 NMT、VMA 与 WDDM。该生命周期带普查，不能当作无诊断的 FPS 基准。

生命周期中额外取得八秒 Nsight Systems 图形吞吐计数，不注入 API、不修改时钟。采集和导出的实际执行区间从生命周期帧分布排除，原始数据仍保留。只解释范围核验通过的整数百分比，其他单位和原始编码不自行猜解。[NVIDIA 导出说明](https://docs.nvidia.com/nsight-systems/UserGuide/#exporting-and-querying-data)支持按指标身份读取这些百分比；整卡计数不自动归属于某个着色器。

21:52:48 起出现另一个 Java 25/Sodium 客户端。H 的静止和其后第一次 E 移动样本与之重叠，保留为受干扰数据，暂停后续组。使用者退出该客户端后，另建 `runtime-final-20261029`。G 的初次加载、飞行、首轮退回菜单和硬件计数早于干扰；重进和后段的全卡／性能数据另行标注。设备丢失与环境干扰分开，没有通过新组自动重试设备丢失。

## 发现

### CPU：保留结果，减少再次组织

[静态区段页](../../components/native_renderer/src/core/render/static_chunk_scene.hpp)在发布时准备 Vulkan 实例模板。每帧批量复制，并修正当前相机平移、实例索引和 SBT 偏移，继续生成相同的运动历史。没有按视锥删除几何，仍遍历实际参与的约 28,820 个静态实例。

[TLAS 输入](../../components/native_renderer/src/core/vulkan/as.cpp)直接保存 Vulkan 实例记录，结束提交时不再生成第二份逐项打包数组。静态模型按页大小的独立所有权组保留 BLAS，动态模型仍独立保留。模型组不拥有材质页，避免复用同一个 TLAS 时延长旧材质发布的寿命；旧材质继续由原有场景及帧完成机制保护。回归覆盖相机大坐标、动态前缀、材料替换、删除、世界身份变化，以及“BLAS 仍有效而旧材质页可退休”。

[元数据版本](../../components/native_renderer/src/core/render/scene_table.hpp)仍创建独立 GPU 版本并保留复制源。目录身份未变时，直接计划连续静态范围的复制，不再为每个静态页创建和查询映射。动态两端继续逐字节判断，目录变化仍处理各页替换。上传、GPU 复制及 shader 连续布局均保留，不能将它称为零复制。

[Java 批次](../../versions/1.21.1-neoforge/src/main/java/com/radiance/api/render/LocalModelBatch.java)将暂存集合纳入现有独占存储池，关闭前清空来源引用。保留两个缓存槽、原生暂存上限及条目高水位限制，Native 接收确认、拒绝处理、纹理代际和多视图边界不变。没有重写实体动画或把来源状态判断全部消除。

默认关闭的 AS 成员追踪改为在遍历之前判断，保留开启后的完整成员记录和默认的创建、销毁、构建事件。这部分减少测试默认诊断的空转；普通实例未开启轻量诊断时，不能重复计算这部分收益。

### 已完成的性能对照

整帧使用 FRAME_ONLY 的开始间隔，按每次运行分别统计；TIMED 用来解释工作，不与其混池。下面的最大值和异常帧均未裁掉。

| 同条件工况 | E 均值 | I 均值 | E／I p95 | E／I p99 | 判断 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1080p 静止 | 24.11 ms | 22.09 ms | 27.03／25.31 ms | 30.09／28.03 ms | 本样本整帧减少 8.4% |
| 1440p 静止 | 25.78 ms | 21.87 ms | 29.68／24.99 ms | 37.30／26.72 ms | 本样本整帧减少 15.2% |
| 1080p 固定移动，首组 E→I | 44.49 ms | 38.97 ms | 62.01／47.30 ms | 75.79／66.59 ms | 轻量窗口改善，详细窗口未复现 |
| 1080p 固定移动，倒序 I→E | 38.25 ms | 39.89 ms | 46.09／47.77 ms | 66.60／67.62 ms | 候选反而较慢，不宣称稳定收益 |

1080p 静止约为真实 41.5→45.3 FPS，1440p 为 38.8→45.7 FPS；没有开启 FG。1080p 最大值为 E 45.24／I 46.89 ms，不支持“所有长帧均已改善”。1440p 的 E 最大间隔为 496.92 ms、I 为 51.49 ms，E 主队列也报告了一个约 320 ms 的最大区间；单次异常不能自动归因于本轮修正，p50 同时从 25.32 降到 21.44 ms，改善并非只由该异常拉动。

对应 1080p TIMED 中，Java 提交／呈现约 7.57→5.48 ms，静态实例追加约 1.56→1.00 ms，TLAS 准备约 1.21 ms 降到 0.2 ms 以下，元数据选择／准备约 1.08→0.55 ms。这些范围存在父子包含，不能直接相加。静态缓存增加约数 MiB 的 CPU 记录，换取逐帧打包、引用和查找工作减少。TLAS 的一部分改善来自默认诊断成员追踪的外提判断；未启用这项诊断的普通 Prism 不能照搬整项省时。

固定移动约每帧都收到新的静态目录发布，两侧约 28,900 个静态实例、33,000 个 TLAS 实例，动态展开仍约 768 个顶点。首组 TIMED 整帧 E 40.12／I 41.57 ms，提交／呈现约 14.78／14.83 ms，SBT 分配／复制记录约 2.48／2.82 ms，I 的目录刷新约 1.69 ms、元数据选择约 1.60 ms。目录持续变化时，本轮“目录不变”的快速路径自然不能普遍命中。倒序轻量复核也未支持稳定收益，到此停止重复，不用两组均值的表面净差盖过运行间波动。不能用静止收益宣称动态加载已解决。

### GPU：主要时间仍在世界 PT

最终 I 的 TIMED GPU 分段如下。主队列为完整区间；子项与模块有包含关系，不能相加成另一个整帧，也不与 CPU 时间相加。

| GPU 工作 | 1080p | 1440p |
| --- | ---: | ---: |
| 主队列完整区间 | 12.62 ms | 20.56 ms |
| 世界主 PT | 9.28 ms | 15.56 ms |
| TLAS 构建 | 0.34 ms | 0.40 ms |
| 实体 BLAS 构建 | 0.08 ms | 0.08 ms |
| SHARC 更新／解析 | 0.55／0.33 ms | 0.82／0.36 ms |
| Vulkan GUI | 0.22 ms | 0.34 ms |
| 最终合成 | 0.015 ms | 0.023 ms |

降噪／重建与色调映射的模块区间另行保留在原始记录。1440p DLSS 模块约 2.33 ms、色调映射约 0.10 ms。1080p 的 E 主队列为 11.95 ms、世界 PT 8.70 ms，I 没有取得 GPU 省时；1440p 的 E 主队列为 21.15 ms、世界 PT 16.17 ms。着色器与第三方运行库未变，分配布局和运行波动都可能影响区间，当前证据不把这些差异定案为某个 shader 或缓存缺陷。

1080p 主要受 CPU 供给限制，1440p 的约 20.6 ms GPU 区间也已接近整帧；即使消除所有 CPU 开销，按这份工作量也不能保证真实 60 FPS。已取得的整卡计数中 GR Active 平均约 53%，SM Issue Active 约 6.4%，显存读／写吞吐约 6.8%／7.8%，PCIe 吞吐约 1.9%。这些均包含 CPU 供给间隙，既不证明算术吞吐饱和，也不能据此精确定位单个 shader 的等待原因。尚未取得逐 shader 的 Nsight Graphics 捕获，不把 GPU 阶段盘点冒充微架构瓶颈已经定案。

全量小资源分池的 G 将 1080p TLAS 区间从约 0.34 ms 推高至约 1.04 ms。退出后的分配图中没有需要长期保留的 AS 存储，因此 I 让 AS 存储继续使用大块池，实测回到约 0.34 ms。没有通过降低采样、反弹、材质质量或完整光追范围取得收益。

### 内存：有效内容、块内空闲和驻留分开

[分配策略](../../components/native_renderer/src/core/vulkan/vma.cpp)以真实 Vulkan 内存需求选择：非专用、非别名、非稀疏且满足大小条件的纯设备本地小图像和缓冲进入每内存类型 4 MiB 的池。保持原来选择的内存类型、对齐和 VMA 的缓冲／图像粒度；AS 存储保留大块分配。池与 VMA 一同退休，不搬移仍在使用的数据。预算扩展只在设备支持并实际启用时使用；否则明确保留原有统计口径。

分配图新增来源操作、资源种类、尺寸／用途名称。原先少量纹理、顶点及索引缓冲分散固定着许多 256 MiB 块。最终 I 全程没有其他游戏重叠，首次退出时 VMA 块约 3.01 GiB，对应 E 旧样本约 6.49 GiB；有效资源分别约 1.72／1.73 GiB。最终一次为 2.76 GiB 块、1.72 GiB 有效资源，E 为约 6.24／1.74 GiB。设备堆块单独为 E 5.77→I 2.29 GiB，其余约 0.47 GiB 为主机堆。主要减少的是块内空闲，不是删除活跃场景。探索 G 的后段有上述环境干扰，最终结论使用无干扰的 I 复核。

以上 VMA 总量包含设备堆及主机堆，不直接等同于独占显存。WDDM 本进程第二次菜单约 E 6.18→I 2.70 GiB。活跃世界的独占显存峰值仅约 13.21→12.74 GiB，共享 GPU 内存峰值约 2.11→1.97 GiB；不能把菜单省下的约 3.5 GiB 当作活跃世界同等收益，更不能据此宣布 4K 预算已经解决。私有提交峰值约 23.19→22.25 GiB、工作集峰值约 9.41→9.23 GiB，这些一次生命周期观察不与 Java 堆或 GPU 驻留相加，也不构成通用峰值承诺。原始资源量、块量和进程计数均保留。

NMT 显示 Java 堆已提交量可高于实际使用量；旧生命周期中约 5.26 GiB 已提交堆对应约 2.7～3.2 GiB 在用，这不是相同大小的存活对象泄漏证据。进程私有提交、物理工作集、JVM 分类、GPU 提交／驻留以及 VMA 块内空闲分别解释；不把这些相互重叠的指标相加。没有强制 GC，也没有通过缩小堆或抛弃来源模型制造占用回落。

剩余驻留包括必要的全局纹理、渲染资源、SBT 等缓存、正常在途资源和驱动资源。图中约 2.8 MiB 的 SBT 缓冲仍可固定较大的普通块，属于可解释的剩余缓存与碎片，没有在本轮用清空所有缓存来掩盖。两个进出周期不支持无限活资源泄漏已复现，也不能证明任意时长、任意模组均无泄漏。

### 加载与实体周期：保留不利结果

I 初次从世界可用到连续十秒无排队及原生工作，约需 161.44 秒，E 为 153.13 秒；重进分别为 61.06／54.05 秒。来源读取、服务器准备与诊断运行波动没有隔离为单一变量，本轮没有初次加载吞吐改善的证据。

I 完成三分钟飞行、七次折返及 128 个实体的创建、运动、删除，两次退出均清空区块跟踪。飞行段带普查平均约 41.32 ms，E 约 46.63 ms，但独立轻量移动对照不稳定，因此不据此另报移动收益。实体移动段为 I 33.24／E 31.06 ms；I 的移除后区间达到约 81.46 ms，E 约 31.27 ms。这一不利结果保留，不以测试正常结束掩盖。

移除后 I 的渲染线程 CPU 平均约 33.86 ms，主队列 GPU 区间从此前约 13 ms 升到约 76 ms。同期 VMA 设备使用约 13,880 MiB，驱动预算一度降至约 12,530 MiB；WDDM 观察到约 1.5～1.94 GiB 共享 GPU 内存。区块队列、在途批次与孤儿资源为零，分配数量和存活字节没有持续上升。现有证据首先指向活跃世界驻留／驱动压力，尚不能证明是实体删除、分池布局或某个 shader 的缺陷，也没有依据归咎于 CPU 普查本身。后续应优先解释这段 GPU 增时，再将小池策略视为已经全面验证的正式性能改进；本轮未部署 Prism。

最终 I 记录 23,413 帧，无丢批、断号、失败帧或观测上限截断，末尾未覆盖约 0.30 秒。整个生命周期中的最长间隔约 5.04 秒包含世界进入／退出边界，不能当作稳定站立帧；分阶段原始长帧均保留。E 旧探针最后约 52 秒缺逐帧数据，只有资源记录完整，该限制不挪作 I 的证明。

### 系统内存与显存的取舍

本轮优先修复分配块驻留，增加的静态 CPU 记录只有数 MiB，不要求把必要 GPU 数据迁回系统内存。1080p 的 CPU 供给和 1440p 接近关键路径的 PT 不适合无依据增加逐帧传输、解压与重建。尚无证据支持实施通用按需换入、全部压缩或显存交换方案；它们不是这次显存降低的来源。

## 结论

当前已证明静止 CPU 提交有可测减少，资源分池能显著降低退回菜单的无效块驻留；尚未证明所有工况都更快，I 的移除后 GPU 增时仍待定案。移动收益不能按静止结果外推；连续发布时的目录刷新、SBT 重组及区块构建记录仍是明确候选。实体来源状态、绑定与批次组织也仍占用 CPU，不能再把约十万逻辑字节的动态顶点上传当成全部 CPU 开销。

E 与 I 展开的 342 个 shader 文件及 14 个第三方运行库逐字节相同，GAME JAR 的 1,112 个类仅 `LocalModelBatch` 与其 `Storage` 改变；Native DLL 为预期变化。I 的 DLL/PDB 标识与年龄匹配，配套源码、全量哈希、命令及中间候选取舍均保留，后续只以 I 作为本轮交付。

已完成的完整构建、发行包和严格合规检查通过，Native CPU 80 项与 GPU 24 项通过；主机功能门槛修正后，诊断组件检查及严格合规再次通过。实际城市、重载和资源周期均正常结束，无设备丢失，但这些不代替使用者的视觉与手感验收，也不等于没有性能退化。不提交、不推送、不改 Prism，未重复 4K 压力运行。
