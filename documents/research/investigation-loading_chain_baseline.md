# 使用者配置的城市加载全链路基准

2026-10-24。按使用者追加要求，在项目内同一纯原版城市副本以 32 视距、32 模拟距离和实际 3840×2160 帧缓冲完成从打开世界到队列平静的连续诊断。最终基准同时对齐 Prism 继承的 512 MiB／16 GiB Java 堆；此前 8 GiB 运行仅为单独保留的校准轮，数据不合并。两轮均正常保存关闭，没有设备丢失。16／1080p 先行运行按使用者决定作废。本轮只补充探针、运行器和证据，不修改产品渲染逻辑，不提交或推送。

## 问题

需要区分进入世界、服务端区块读取／生成、客户端编译、原生准备、GPU 完成及最终平静，而不是只在加载结束后取一段 FPS。还需要知道现有 CPU 至 GPU 的计时覆盖和剩余缺口。此基准使用使用者的实际配置，不能继续套用先前城市场景约 23.5 ms 的旧配置结果。

## 方法

产品沿用实际验证并投放过的冻结包，未重建产品：

| 输入 | SHA-256 |
| --- | --- |
| 产品 `takeover-incremental-final/radiance.jar` | `2b68c395760d0789f6af48d83002ee39327da03a685f4a3b5055b37456b8b67a` |
| 本轮独立 probe | `8b2ee75ba73b05c1ff1e5c405c70a59e42876c5e83d86561e46aa2961bbecb28` |
| 已有纯原版城市夹具 | `8a7f468828b8aca4ed51bbd31ce203ee71d82b85284af56a7128baf8f8dc10dc` |
| `prism_rendering_baseline` 配置输入 | `5ccfbf65d7ad9a04d763549ff9b1798313a9d63bca943baee5b0957fc8f35e76` |
| 实际加载的 core.dll | `45c3517cf51b471783361d2e3d6bcd642ff980fe30697649b6556f6eb00153ca` |

8 GiB 校准清单为 `validations/performance-vanilla/result/loading-chain-manifest.json`，案例为同目录的 `loading-chain-r32-2160-20261024-121438`。最终正式清单为 `loading-chain-runtime-manifest.json`，案例为 `loading-chain-runtime-r32-2160-20261024-125140`。各自保存独立的 `loading-chain-analysis.json`、`worker-whole-capture.json`、`loading-chain.jsonl`、`loaded-core.json` 和 `raw-evidence.zip`，不得混合统计。原始 CSV／日志逐条读回校验 SHA-256 后归档，JFR 原文件保留；较早两份 JFR 按 SHA-256 校验迁至 `validations/performance-vanilla/result/chunk-pipeline/relocated-evidence/loading-chain-20261024/`，案例中的 jfr-relocation.json 给出准确路径。客户端副本正常关闭后送入回收站，不保留重复运行库和世界副本。

运行配置输入 `prism_runtime_baseline` 的 SHA-256 为 `3a9bea919a5796f863abbd88a06758ed6affc4f9946aadc5766b910c52681d7b`。仅复制内存／Java 等白名单字段：Prism 未启用实例内存覆盖，继承全局最小 512 MiB、最大 16,384 MiB，无附加 JVM 参数，Java 21.0.11。正式轮的 actual-vm-flags.txt 独立确认 InitialHeapSize=536870912、MaxHeapSize=17179869184。准备时一次存储预检拒绝启动；按校验迁出旧 JFR 后才启动正式轮，不是 GPU 故障后的重试。

配置输入在停止的授权 Prism 实例上持有原子实例锁只读复制，22 个文件分别核对，包含 options.txt、Radiance 主设置、管线、独立着色器设置和 config 文本。没有复制模组、运行库或新世界，也未修改 Prism。输入在 inputs.toml 登记，本机路径只在 local.toml。世界继续使用先前冻结的纯原版城市。

配置来源是 16 视距、32 模拟距离；使用者明确追加改为 32／3840×2160。自动运行另外覆盖主音量 0、失焦不暂停和窗口模式，保留原画质、实体距离倍率、调度线程／批次、Reflex 与着色器参数。实际活动属性确认：Vanilla PT、DLSS SR Balanced、SHARC 开启、FG 关闭、随机覆盖、反弹上限 128、间接光强度 16。主设置的 rayBounces=4 与包内活动属性 128 分别保留，本次没有擅自统一；运行证据使用后者，不把主设置文件当作全部实际配置。

在逻辑服务端执行原命令 `tp @s 0 512 0 facing 0 0 0`。原版整数位置参数将 X/Z 居中，实际位置 `(0.5,512,0.5)`，yaw=-90、pitch=90；夹具原有创造飞行保留。随后静止，不操作地形、实体或画质。没有清空系统磁盘缓存或驱动缓存，所以不称为冷磁盘测试。

使用一个连续 TIMED 窗口和有界 JFR，保留打开世界的长间隔。旧逐区段 trace 会影响静态场景准备路径，本轮保持关闭；异步 GPU 查询不等待读取。Java 工作线程和 native worker 的 frame=0 表示没有渲染帧归属，整轮统计其调用分布，不硬摊进各帧或阶段。CPU 墙钟、线程 CPU 活跃、工作量累计与 GPU 区间分开。

## 发现

以下至“16 GiB 正式轮”之前均为 **8 GiB 校准轮** 的独立结果，不作为最终 Prism 运行配置的性能结论。后续发现内存继承差异后，使用同一产品、探针、世界与渲染配置完成正式轮；改变了 Java 堆和运行时刻，且没有交替重复，不能从两轮差值推导堆大小的因果收益。

### 采集入口与收尾

先行 `loading-chain-r16-1080-20261024-120642` 已按使用者决定标记作废。它正常保存退出且无设备丢失，但探针误等精确 `(0,512,0)`、异步统计写盘未等待完成，不能作为有效性能样本。重测前修正为原版居中位置，停止采集在下一帧边界执行，等待 STATUS 写完再退出。作废清单、原始日志和收尾分析失败仍保留，不用成功重测覆盖事实。

8 GiB 校准轮采集 5,003 帧，expected=recorded，帧号无缺口，writer/native/output-cap 丢弃均为 0，Java 分区错误和失败帧均为 0。首次 GPU 部分读回遗漏明确报告一次；平静段有 458 个 GPU 返回帧对应 460 个 CPU 帧，未返回尾部不补零。正常保存、正常 native close 的独立跟踪及 core 加载身份均保留。

中间出现两次短暂恢复的区块工作，分别打断较早的平静候选，因此没有挑选较早的短窗充当最终平静。这里的“平静”是队列／活动观测，不代表降噪视觉完全收敛、每个区段都已被扫描输出或画面通过人工验收。

整轮记录到 7,759 次磁盘数据加载事件、4,761 次新生成区块加载事件、3,653 次客户端列到达回调。它们是事件次数，不保证唯一坐标；NeoForge 21.1.259 的 ChunkEvent.Load.isNewChunk 合同明确只会在逻辑服务端返回 true。不能把本轮解释成只读取已有区块的纯客户端测试。

### 帧时间与渲染线程

| 窗口 | CPU 帧数 | 真实帧间隔均值 ms | p95 ms | p99 ms | 渲染线程活跃均值 ms | 主 GPU 队列区间均值 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 固定相机后加载及平静建立 | 4,320 | 38.66 | 55.24 | 66.44 | 33.48 | 32.88 |
| 最终队列平静 | 460 | 44.33 | 47.17 | 50.08 | 23.51 | 43.84 |

平静段约 22.56 真实 FPS，包含 TIMED／JFR 诊断开销，不是无探针的净性能样本，也不是某项优化的 A/B 收益。加载时场景逐步进入，两个窗口不是同一几何内容，不能因加载段平均更快就判断加载更高效。进入／传送段保留 5,554 ms 的最大帧起点间隔，没有用预热过滤掉。

平静段 CPU 墙钟中，实体基础剩余分区约 3.61 ms、状态 1.07 ms、部件绑定 0.89 ms、批次打包 1.15 ms、输出 0.55 ms、BER 1.67 ms、客户端 tick 2.50 ms。它们是渲染线程分区；与下面的 native 深入拆分不可重复相加。FRAME_OTHER 墙钟约 20.48 ms，不能当作等量 CPU 计算；整体线程活跃约 23.51 ms，而帧间隔约 44.33 ms。

JFR 的 JNI 边界样本定位到 submitCommandNative、streamlineFrameEvent 和 acquireContextNative。源码中 streamlineFrameEvent(0) 调用 Reflex beginFrame/slReflexSleep；本配置 Reflex mode=2。该证据支持存在节拍／等待，但未单独计时 slReflexSleep，不能把 FRAME_OTHER 全部归因于它或声称这部分可直接删除。JFR 在启动时记录的主线程名为 main（Java thread id=1），调用栈确认它就是 Minecraft 渲染线程，不按旧名字漏掉样本。

原生输入统计与独立累计计数一致。共构建／提交／完成 5,135 个批次：CPU 批次准备累计 4.217 s，约 0.821 ms／批；提交累计 0.169 s，约 0.033 ms／批；提交至观察到完成累计 179.407 s，约 34.94 ms／批。最后一项包含队列排队、GPU 工作和轮询，不能写成纯 GPU BLAS 构建耗时。编译／入队数高于最终驻留数，可能包括邻区依赖、替换、空输出或过时结果，尚未逐身份归因，不直接认定全部是浪费。

加载段 native 静态场景刷新均值约 6.06 ms／渲染帧，SBT 分配／复制／录制约 1.18 ms。平静后，静态实例追加约 1.32 ms、TLAS 输入／构建录制约 1.17 ms、刚性元数据约 0.77 ms、元数据内容选择约 0.47 ms；这是 Java submit 内部的深入拆分。数据到达结束到区块工作结束的长尾，仍需结合按帧 2 ms 准入预算、实际编译／拓扑成本、重复版本和 GPU 排队分析，不从一次观察直接宣布根因。

## 结论

正式结论只使用对齐 Prism 内存配置的 16 GiB 轮：约 60.8 s 后仍有长时间客户端编译／原生发布尾部，约 153.3 s 最后观察到区块活动，163.75 s 确认队列平静。最终约 21 秒窗口平均 70.90 ms，GPU 主队列 70.25 ms、整卡显存接近容量；这不是已经稳定的最终 FPS。16／1080p 作废轮和 8 GiB 校准轮分别保留，不拼接、不据其差值宣布优化收益或堆大小因果。当前没有证明单一根因，没有修改产品渲染行为、降低质量、修改 Reflex，也没有故障后重试。

现有设施可以列出大部分 CPU→GPU 主链路，但不能宣称已精确计时每个区块的所有阶段。尤其缺少独立区块 GPU 区间和逐更新身份的首次使用链；后续如继续补强，应以这些明确缺口为目标，而不是重建另一套大型诊断框架。接管层增量实现、GUI 人工验收和其他暂缓工作保持原范围。
