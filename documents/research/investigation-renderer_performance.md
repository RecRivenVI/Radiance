# 无 Voxy 城市 CPU、GPU 与内存调查

2026-10-29，本轮在同一冻结城市和既有配套上调查加载、静止、持续移动、实体寿命及退出重进。主要稳态限制是世界 PT，退出世界后的分配块碎片也有直接证据；没有修改产品渲染、分配策略或画质，没有提交、推送或操作 Prism。

## 问题

需要区分接管后的来源求值、提交、等待与真正的 GPU 工作，并解释 32 视距的内存占用。不能把持久命中率当成 FPS，不能把整卡显存、进程提交内存或 VMA 分配量混为一谈，也不能用强制清空缓存证明没有泄漏。

## 方法

### 冻结输入与观察口径

- 产品是[来源效率 E 清单](../../validations/conformance-takeover/result/source-efficiency-20261029/source-efficiency-e-20261029/candidate.json)中的本体、Extra 和 Native。Core SHA-256 为 `ca9eaf378b91ff0552178a8e6457065a89bd93f0fd07fd0d94bc3b24a5049e7a`；Extra 为 `1093201e7a4c37647aef4dbfee4049b2513d871115b8c44ffbd35c701a3aea85`；实际 DLL 为 `def55b70140079601c21a20dbd52609202292663015c3286c496dd574e4ef1a6`。
- 城市输入为 `validations/migration-city_world/result/vanilla-city-fixture.zip`，SHA-256 为 `832a650f7dc6ecba23822d49d767fd0a609f00b3faff6df3f657e2cced0f723e`。每次从同一输入新建验证副本，不修改来源存档。
- NeoForge 21.1.259、Java 21、RTX 4080 SUPER 16 GiB、驱动 621.01；加载 Core 和 Extra，不加载 Voxy 或其他兼容目标模组。
- 32 视距、同一原版 PT、SHARC、四次反弹、随机覆盖半透明、DLSS Balanced、FG 关闭。分辨率表是输出尺寸比较，不能写成原生一比一着色分辨率。自动实例静音、无失焦暂停；保存相机、实际尺寸和来源兼容检查。
- 静止窗口使用夹具保存的相机：位置约 `(95.784, 143.227, 12.897)`，yaw `53.535`、pitch `32.749`。加载链另按原有命令移到 `(0.5, 512, 0.5)` 向下观察；两者画面和 FPS 不直接比较。
- FRAME_ONLY 只用于低开销帧间隔；TIMED 用非阻塞 GPU 时间戳和分段计时归因；JFR、内容审计及分配普查单独标注。Java／Native 包含关系及 GPU 范围不能相加，GPU 缺样不补零。
- Nsight Systems 的整卡硬件计数在 720p 两个正式窗口之间采集，没有注入 CUDA 或改动着色器。它证明设备状态，不把整卡计数直接归属于某个函数。
- 生命周期用独立探针、1 Hz 资源记录、JVM NMT 和 WDDM 进程计数，持续飞行约三分钟，创建／移动／移除 128 个诊断实体，再退出和重进。没有强制 GC、清空渲染缓存或驱动缓存。

### 诊断自身的对照

因使用者观察到个位数 FPS，另做同一冻结产品、相机和设置的最小控制运行。关闭所有来源／渲染审计 Mixin、Native 采集器和 Aftermath，仅保留一个外层 `runTick` 控制与计时钩子；运行时日志确认 `aftermathFlags=0`、`diagnosticsConfig=0`。CPU 侧故障面包屑仍保留，不称为完全无观察者。

轻量 FRAME_ONLY 平均为 **170.21 ms（5.87 FPS）**；最小控制为 **169.85 ms（5.89 FPS）**。此处差异约 0.2%，不能解释个位数帧率。JFR 采样仍有明显扰动：采样窗口的观察器 begin-frame 平均约 6.48 ms，不能用该窗口的耗时替代正式基线。

## 发现

### GPU 是当前稳态主限制

| 输出尺寸 | FRAME_ONLY 平均 | p95 | 实际渲染 FPS | TIMED 世界 PT | TIMED 主队列 |
| --- | --- | --- | --- | --- | --- |
| 1280×720 | 82.54 ms | 88.31 ms | 12.11 | 71.15 ms | 78.17 ms |
| 1920×1080 | 170.21 ms | 177.06 ms | 5.87 | 161.36 ms | 172.49 ms |
| 2560×1440 | 288.73 ms | 327.20 ms | 3.46 | 262.11 ms | 281.34 ms |

FRAME_ONLY 与 TIMED 是前后两个窗口，上表不能当作同一帧的可加拆分。另一个 1080p TIMED 窗口平均 163.59 ms，世界 PT 为 154.47 ms、SHARC 更新 5.76 ms、DLSS 1.28 ms、TLAS 构建 0.45 ms、GUI 0.24 ms、实体 BLAS 0.15 ms。世界 PT 显著高于其他阶段；不能把 GUI、超分或顶点生成当成本场景的首要瓶颈。

720p 独立硬件捕获中，GR Active 98.71%、SM Active 91.54%，但 SM Issue 只有 1.68%，计算驻留吞吐约 23.30%；DRAM 读／写吞吐约 26.17%／26.42%，PCIe RX 约 2.56%。GPU 确实繁忙，却不能据此断言算术单元或显存连续带宽已经饱和。RT 遍历、依赖等待、寄存器和访存延迟仍是候选，本轮没有逐着色器 RT 单元或 stall 归因。

分辨率变化足以支持渲染本身已经成为瓶颈。没有执行 2160p 压力运行：已有 1080p／1440p 整卡占用接近 16 GiB，继续加压不足以解决当前归因问题。本轮也不能证明硬件的理论 FPS 上限，更不能据这些 GPU 时间承诺 60 或 120 FPS。

### CPU 主要在等 GPU，但仍有真实工作

1080p 基线渲染线程实际 CPU 活跃均值约 38.27 ms；720p 为 28.97 ms，1440p 为 40.56 ms。Windows 线程 CPU 时钟在本机呈 15.625 ms 量化，单帧 CPU 数字不能作精细减法，使用窗口均值和采样相互核对。

1080p TIMED 的 Java `ACQUIRE` 约 126.49 ms，包含 Native fence 等待约 125.49 ms；这些是等待时间，不是 CPU 正在计算。JFR 的渲染线程样本 166 个，其中 110 个处在 Native acquire，支持这一判断，但采样次数不能换算成对应毫秒。

同一 TIMED 窗口的主要非等待工作包括：客户端 tick 8.82 ms、提交／呈现 10.59 ms、来源状态 2.65 ms、实例打包 2.20 ms、方块实体 2.02 ms、实体主体 1.83 ms、实体输出 1.81 ms、部件绑定 1.42 ms、辅助纹理 1.24 ms。提交内还有静态实例追加 1.56 ms、TLAS 命令组织 1.30 ms、元数据内容选择 1.21 ms、刚性元数据 0.84 ms、SBT 分配／复制／记录 0.86 ms。后面这些是前面阶段的内部细分，不能重复相加。

低 FPS 下每帧可能执行多个游戏 tick；8.82 ms 不是未来 60 FPS 下不变的每帧底价。因此不能把本轮 CPU 活跃时间取倒数，直接写成 CPU 的绝对帧率上限。

来源统计中，每帧约 369 次盔甲架、293 次物品展示框、223 次画、46 次矿车和 32 次船来源调用。盔甲架与展示框的来源自身时间约 1.72／0.73 ms 每帧，是可继续调查的来源，但已经不是全量几何重新展开：

- 每帧约 4,128 个选中刚性实例，约 257 个持久实例发生参数更新；约 94% 的选中状态没有变化。
- 稳定引用约 178,099 个顶点；Java 本帧实际生成 PBR 顶点仅 816 个、104,448 个逻辑字节。
- 354 个驻留刚性模型约 6.3 MB；持久实例驻留记录约 12,735 个，含其他选择／历史状态，不等于当帧选中数量，也不自动等于泄漏。
- 约 28,820 个静态区段、47,561 个静态几何及 32,950 个 TLAS 实例。平静窗口静态重建为零，静态内容复用确实生效；逐视图追加、选择、历史及 TLAS 输入仍有成本。
- SBT 每帧约四次请求、3.76 次复用和 0.25 次冷上传，不能写成每帧重传四整份 SBT。元数据逻辑主机上传约 2.4 MB、另有 GPU 内部复制／总更新范围，不能当作实测 PCIe 流量。

### 加载没有全部卡在世界生成

独立加载链在点击打开世界后约 7.33 秒建立玩家世界，8.59 秒固定到高空相机；最后观察到磁盘反序列化、新服务端区块与客户端列到达是在 62.15 秒附近。最后原生批次活动约 156.26 秒，之后满足十秒无活动并继续观察二十秒，189.11 秒正常停止。数据到达与最后构建活动相差约 94 秒，是后续渲染流水线调查入口，不代表其中每一毫秒都在编译。

本次记录 7,759 次磁盘加载事件、4,761 次 `ChunkEvent.Load.isNewChunk()` 事件及 3,653 次客户端列到达；这些是不同层的事件计数，不是互斥的唯一对象总数，确认本次包含新生成，不能标为纯存档读取基准。

原生累计接收 30,755 份构建输入，输入 CPU 工作约 13.87 秒；3,939 个批次准备累计约 3.55 秒、提交约 0.12 秒。批次提交至完成的累计墙时约 263.98 秒，包含并行重叠、排队和完成轮询，既不是独立 GPU 构建时间，也不能与加载总时长相加。最后有效区段 28,391，所有记录队列平静。

加载／收敛阶段平均 80.82 ms，p95 99.21 ms、p99 103.79 ms、最长 228.26 ms；进入和传送阶段另有约 5.87 秒长间隔，完整保留。高空平静窗口平均 92.93 ms，与楼房相机约 170 ms 是不同可见路径，不是优化前后。

当前已有实时时间片上传节流、在途预算及后台准备，不能再把它描述成旧的单纯逐帧限批次。仍缺每个区段从版本准入到首个实际使用帧的身份关联，以及独立区块队列 GPU 时间；这些边界不足以判定哪一段应直接增加线程。

### 移动、实体压力和退出重进

真实按键飞行在 Y=384、X 方向约 ±128 方块往返 180.3 秒，完成七次转向，避免第一次尝试在建筑上碰撞后停住。返回保存相机后再进行实体压力，不能拿高空飞行平均约 48.66 ms 对比楼房静止并声称移动更快。

128 个诊断实体是 64 个盔甲架和 64 个无 AI 僵尸，先静止约二十秒、再以 5 Hz 更新位置与旋转三十秒，随后移除观察四十秒。移动阶段 p95 约 445 ms、移除后仍约 482 ms，表明长帧未随实体删除立即消失。由于这是连续的内存寿命压力序列，没有随机交替实体 A/B，不能将全部退化归因于新增实体或其发光。

第一次生命周期尝试因路线碰撞未满足位移／转向条件而被工具判失败，正常保存退出，没有设备丢失。证据保留后改用高空路线完成独立用例。有效生命周期含第一次世界平静约 230 秒、重进约 275 秒；分配普查和 NMT 在场，不将其直接当作轻量加载基线。

生命周期最初每帧的平静检查与 1 Hz 记录都会消费原生累计计数，导致那一次的原生工作差量不完整。队列状态、帧间隔、内存与实际路线仍有效；本轮已改为共享同一秒快照，并用前述独立加载链补齐累计工作，未重写旧数据。分析器也改用每帧的 UTC 起点，避免打开／退出世界的帧间空档使后续阶段错位；跨阶段的长帧不归到某个阶段内部，原始全程数据仍保留。

### 显存既有有效内容，也有可处理的分配块碎片

静止后区块跟踪缓冲约 **8.87 GiB**，115,280 个缓冲；平静后没有已移除却仍被区块跟踪器孤立持有的缓冲。全部 VMA 设备块约 10.71 GiB、有效分配约 10.39 GiB，另有主机可见分配。完整光追场景与着色属性本身就有很大驻留需求。

生命周期中 WDDM 本进程专用 GPU 内存从静止约 11.99 GiB 增至返回后约 12.50 GiB，Shared 从约 1.05 GiB 增至约 2.55 GiB。Shared 可以包含主动使用的主机可见资源，不能单凭此项判定发生了驱动换页。NVML 的约 15.5～15.8 GiB 是整卡数值，还含其他应用及驱动；没有把差值全部算给 Minecraft。

退出世界确实释放了区块：跟踪数回到零，VMA 设备有效分配回到约 1.35 GiB，主机有效分配约 0.30 GiB。但总分配块没有同幅度回落：

| VMA 场景释放快照 | 块总字节 | 有效分配字节 | 含义 |
| --- | --- | --- | --- |
| 首次进入前 | 2,070,790,144 | 1,685,546,432 | 初始加载后基点 |
| 首次退出世界 | 4,822,253,568 | 1,760,561,936 | 约 3.06 GB 空隙仍在块内 |
| 第二次退出世界 | 5,090,689,024 | 1,764,922,128 | 有效量稳定，块增长至约 4.74 GiB |

分配图直接显示：设备本地的 256 MiB 块可能仅剩一张 16 KiB `IMAGE_OPTIMAL`，或四张各 8 KiB 的图像；也有少量小型 GUI 顶点／索引缓冲。有效资源仍占住块，VMA 不能把整块还给驱动。这是长期小资源与大场景分配混用导致的块内碎片证据；尚未将每张图像映射到确切产品所有者，不能全部归咎于 GUI。

VMA 有效分配在两次退出后约 1.64 GiB，基本稳定。本轮支持“世界内容已释放，但块驻留／碎片仍偏大”，不支持“无限活资源泄漏已复现”，也不足以证明任意长期运行没有泄漏。

另一个计量限制来自[当前分配器](../../components/native_renderer/src/core/vulkan/vma.cpp)：仅启用 `BUFFER_DEVICE_ADDRESS`，没有启用 VMA 的 `EXT_MEMORY_BUDGET` 标志。现有 VMA budget 输出走后备估算，不能当成操作系统报告的实际可用显存预算；驻留判断以 WDDM／整卡观测分别说明。

### 系统内存不能用一个数字定性

生命周期进程 Private Bytes 最高约 22.15 GiB，阶段均值最高约 21.8 GiB，首次回菜单约 12.6 GiB、最后回菜单约 13.4 GiB；它是私有提交量，不是物理工作集。实测物理工作集峰值约 9.0 GiB，不能把两种数字互相替代。Java 堆实际使用约 2～3 GiB，但 G1 已提交堆从不足 1 GiB 增至约 4 GiB，未强制 GC，保留提交并不等于对象泄漏；`-Xmx8G` 是上限而非实时占用。

JDK NMT 只覆盖其认识的 JVM 内存，不能覆盖全部 JNI／驱动分配。不能用进程 Private Bytes 减 NMT 后，把剩余量直接宣布为 Native 泄漏。Java 直接缓冲池也不是整个 Vulkan 主机内存的代表。

### NVIDIA 变量控制

按本轮授权，已在用户级 Codex 配置登记 `nvidia-app` Streamable HTTP 服务并验证 initialize／工具枚举。服务可读覆盖层、录制和驱动状态，但没有细粒度 3D 配置接口；读取的 RTX HDR／DVC、锐化、录制和性能覆盖层均关闭。只读 NVAPI 查询没有取得 Vulkan/OpenGL present method 的当前值，不能把“未查到设置”解释成 Auto 或原生优先。本轮没有修改 NVIDIA 图形设置。

## 结论

### 建议的后续顺序

1. **先降低显存块碎片并获得真实预算。** 沿现有 VMA 分配机制区分长寿命小图像／GUI 缓冲与大型场景分配，先查明占块对象，再做有限寿命分组或 pool 对照。保留在途退休，不清空全部缓存。目标是降低块峰值与退出残留；是否改善帧时长另测。
2. **针对世界 PT 做有限的结构性实验。** [区块 BLAS](../../components/native_renderer/src/core/render/chunks.cpp)当前是 `PREFER_FAST_BUILD`，实体和 LoD 已使用 `PREFER_FAST_TRACE`。长期静态区块值得比较 fast-trace 及构建后压缩，分别测加载延迟、AS 大小和稳态追踪；它们是候选，不是已证实根因。[NVIDIA 的 RTX 建议](https://developer.nvidia.com/blog/best-practices-using-nvidia-rtx-ray-tracing/)支持按更新频率选择构建策略并评估压缩，不能据此预报收益。
3. **进一步定位 PT 遍历和属性访问。** 在不减内容、精度和反弹的前提下，区分遍历、any-hit、材质读取及 shader 依赖。当前硬件计数没有给出这一层归因。可评估重复属性的无损表述与常量复用，但位置／材质缓冲还有着色和历史消费者，不能在 AS 建好后直接释放；lightmap 等字段也仍有实际语义，不能盲删。
4. **CPU 聚焦实际残余工作。** 来源状态／绑定、未变实例的选择与逐视图静态追加仍有成本；先用现有计数限定对象。客户端 tick 与渲染等待分别处理，不再将主要预算投向本场景已很少的 Java 顶点生成。加载则补齐版本到首用的延迟与独立队列计时，避免把 94 秒尾部一概归到 CPU 编译或直接增加线程。
5. **暂不将场景数据普遍搬回系统内存。** 全几何 PT 随时可能查询相机外内容；主机副本、压缩与按需上传只有在实际访问／更新频率可解释时才考虑。先减少碎片和冗余表达，再比较带宽、同步与重新构建，防止换出显存后造成更长停顿。

本轮没有取得新产品优化前后的收益，也没有证明硬件最终上限。已确认旧持久路径确实减少生产，但当前场景仍需显著缩短 GPU PT 才能接近真实 60 FPS；60 FPS 的 16.67 ms 和 120 FPS 的 8.33 ms 不能靠此次个位数诊断数据承诺。
