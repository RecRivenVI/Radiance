# 城市场景 GPU 帧预算与帧率边界

2026-10-18，按使用者授权将 GPU 帧时长纳入同城盘点，检查当前硬件上的优化候选及可证明边界。本项区分当前实现的 GPU 预算、假设 CPU 不再限制后的条件性吞吐和保持画质的算法优化空间，不把测量值写成硬件不可突破的理论极限。

## 问题

此前静态表实验的最终 CPU 窗口有 1,646 帧，GPU 仅返回 1,644 帧。旧分析按 CPU 总帧数摊销 GPU 时间，主队列为 16.041 ms；按有效 GPU 样本重新计算为 16.061 ms。两帧未返回不能补零。真实帧间隔 36.465 ms、GPU 完成区间及 SDK 的生成帧率不是同一指标。

目标为固定城市场景、完整几何和相同画质下的真实 60／120 FPS，分别对应 16.667／8.333 ms。此次不减少视距、采样或反弹，不停止模型更新，不恢复已退休的独立场景回放，不实施动态模型或 shader 优化。

## 方法

### 证据与配置

沿用[静态表实验](experiment-static_scene_tables.md)的完整源码及候选身份。原始 GPU 数据为 `validations/performance-scene_diagnosis/result/profiles/2026-10-17T20-04-16.924282600Z-pid80824/`。新工具与运行证据由同项验证的 `result/gpu-inventory-20261018/` 保存，临时工具位于 `D:/Workspaces/Scratches/RadianceSemanticsAudit/`。

本机查询为 Intel Core i7-14700K、NVIDIA GeForce RTX 4080 SUPER、16,376 MiB、驱动 617.14；另有其他项目客户端，允许存在的外部负载仍记录，不操作其进程。测试为项目内实例、1920×1080、32 视距和模拟距离、Vanilla PT、RR Balanced、Reflex 2、FG 关闭、静音、相同保存相机。世界 ZIP 按原清单逐文件恢复校验，固定输入不等于逐 tick 相同动画。

### 测量边界

现有 GPU 查询池在对应帧 fence 后读回，新增采集沿用其非阻塞 availability 路径和 96 个区间容量。command buffer、世界模块与 PT pass 嵌套，不相加；时间戳是 GPU 队列完成区间，可能包含同步与调度等待，不等于 SM 忙碌时间。主队列窗口不覆盖独立区块队列及全部 SDK 内部工作。

计时语义对照 [Khronos 时间戳示例](https://docs.vulkan.org/samples/latest/samples/api/timestamp_queries/README.html)；吞吐、队列利用及 shader 活跃状态需要 [Nsight GPU Trace](https://docs.nvidia.com/nsight-graphics/UserGuide/gpu-trace-overview.html) 和 [Shader Profiler](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html) 等证据，不能由时间戳差值反推出硬件利用率。

本项只补 profile 激活期间的 `sharc-update-gpu`、`sharc-resolve-gpu` 及实际追踪宽高深计数。解析区间包含现有更新到解析的依赖屏障；没有新增 wait、idle、同步屏障或改变着色器。计时插桩仍可能扰动 GPU 重叠，须注明后才能比较。

既有 `pt-pass/world` 包含该 pass 的参数上传、资源屏障和追踪，不是单独的 shader ALU 时间。现有表也未独立覆盖每一段准备／屏障，更未覆盖 PT 内部每种射线与材质；不能把父区间减去子区间的差额直接解释成 GPU 空闲。

### 硬件计数器尝试

已读取本机 Nsight Graphics 2026.3.0 的命令行帮助，以 `GPU Trace Profiler`、Ada Throughput Metrics、最多 4 帧／250 ms 尝试一次采集；`--set-gpu-clocks unaltered`，不修改时钟、TDR 或系统权限。PID 62916 在 SERVICE 设备创建阶段连接成功，但工具报告 `GPU Performance Counters unavailable`，随即终止会话，没有取得 GPU Trace／shader 瓶颈数据，也没有进入世界。

该次启动前，旧临时恢复脚本因同目录 `inspect.py` 遮蔽标准库而失败；这次工具预检不能算固定夹具运行。随后使用 Python 隔离导入模式 `-I` 正确恢复并逐文件核对夹具，才准备正常时间戳采样。命令导出还留存首次 Gradle init script 的 included-build 定位错误及后续主动阻止 Java 启动的记录；这些不是产品编译或世界验收失败。

没有为工具接通改用关闭 SDK 的配置，没有重试硬件采集，没有更改全局计数器访问权限。工具日志、进程退出和正常客户端结果分别记录。

### 优化候选与证据等级

1. 世界 PT 是已测量的 GPU 首要宽阶段；any-hit 材质／层选择、透明续接、次级射线和 SHARC 查询在同一 pass 内，尚无硬件采样把成本分配到它们。源码路径存在不等于它解释了全部 11 ms。
2. `sharcCapacity = 1u << 23`，解析每帧派发 131,072 个 64 线程工作组。第三方实现先读键，再对空项返回；这是按容量的检查，不能称为每项都完成昂贵解析。实际解析约 0.160 ms，更新约 0.217 ms；暂不优先改写。若后续优化为活动项处理，必须保留老化、冲突迁移、失效和历史，不以缩小缓存制造收益。
3. 普通覆盖模式可对背景分层继续执行完整照明；减少重复材质读取、射线活跃状态及等价计算值得评估，但不能减少合法层、反弹或传光。
4. 实体 BLAS／TLAS 和上传仍有成本，持久几何可能减少它们；增加实例也可能提高遍历成本。GPU 顶点转换约 0.04 ms，不适合作为本场景的主要 GPU 提速目标。
5. DLSS 是已测模块区间，不据此承诺能够优化闭源 SDK，也不关闭 RR 后将结果算作原画质通过。

### 帧率边界的定义

`1000 / GPU 区间` 只是在“工作、时钟、调度和同步代价保持不变，CPU 已能持续供给”的假设下的预算参考。已有整体均值对应约 62.3 FPS，p95／p99 区间分别超过 60 FPS 的帧预算；不是稳定 60 FPS 的证明，更不是任何未来等价实现的硬件上限。

新窗口整体均值对应约 59.2 FPS 的条件性预算参考，p95／p99 约对应 47.6／43.1 FPS 的预算倒数；这些不是实际 1% low 或已达到的帧率。两轮均值预算约 59～62 FPS，不能当作硬件上限范围。

120 FPS 要求整体 8.333 ms；当前世界 PT 自身已超过此预算。因此仅消除 CPU 顶点生产不能满足，必须同时显著降低 GPU 成本。若只作灵敏度分析，固定新窗口其他区间的合计差额约 4.805 ms，则世界 PT 需从 12.073 降到约 3.528 ms、减少约 70.8%，总 GPU 区间需减少约 50.6%。这不是等价改动实验，也不承诺差额能独立保持。不能把“理想删除某些阶段”称为可实现或语义等价的测试。

真正不可突破的硬件上限需要证明必要工作量及资源下界。当前没有实际射线／any-hit／材质命中分布、必要访存量、SM／RT Core／缓存吞吐和最优调度证明；硬件峰值算力与显存带宽不能直接换成 FPS。GPU 时间戳与一次成功运行都不能补足这些条件。

## 结论

已完成 GPU 分段盘点与一次正常配置城市采样。世界 PT 是 GPU 首要宽阶段；SHARC 全容量解析存在但本场景成本较小，GPU 顶点转换也不是主要目标。下一步 GPU 调查应优先区分世界 PT 内部的遍历／any-hit、材质访存、透明续接和活跃状态，而不是仅凭源码循环或硬件支持立即接入 SER、改写 SHARC 或减少质量。

GPU 必须与 CPU 同时纳入帧预算。现有数据仅支持当前实现约 59～62 FPS 的平均 GPU 预算参考，未证明稳定 60 FPS，也未证明任何保持语义的未来实现不能达到 120 FPS。驱动硬件计数权限仍是区分 SM、RT Core、缓存／带宽及调度瓶颈的明确外部缺口；尚不能给出可证明的硬件理论上限。此次不以未知项启动新的大规模优化，不提交或推送。
