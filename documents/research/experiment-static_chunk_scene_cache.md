# 静态区块场景快照与城市对照

调查日期：2026-10-15。本轮只减少主世界静态区块逐帧重复组织；动态几何转换、着色器、画质与查询规则未修改。16 视距取得组织成本下降证据；32 视距参考轮出现非设备丢失长停顿，未取得有效稳态对照，不能宣布完整性能验收通过。

## 问题

[上一组城市测量](investigation-city_distance_loading_comparison.md)中，单区块元数据缓存已命中，但每帧仍遍历全部容量槽位，逐区块取得快照、保活资源并追加地址、材质、命中组和实例记录。32 视距的相关 CPU 自身耗时约 19 ms/帧。此数值是调查入口，不当作本轮同条件参考。

使用者授权先优化静态组织，保留完整 PT 几何、既有成像和传光语义、外部结构历史、代际保护及资源退休。发生设备丢失必须停止整组；不提交、不推送、不操作 Prism 或旧 MCVR 仓库。

## 方法

### 实施边界

- `static_chunk_scene.hpp` 定义有效发布集合、不可变快照与实际用于产品的批量追加接缝。
- 主区块接受发布、删除、重定位或释放发光资源时更新集合版本。标脏但新几何未就绪时保留有效旧几何；被拒绝的旧发布不更新集合。
- 世界重置使用新的集合身份，防止相同槽位或版本数值造成 ABA。外部区段不进入主区块快照，继续使用完整句柄和原有变换历史。
- 快照缓存按槽位排序的地址、材质、来源面规则及命中组；动态实体、刚性实例和 Flywheel 仍先组织，批量追加时按本帧前缀调整几何与 SBT 偏移，不改变实例次序。
- 每帧仍计算双精度相减后的相机相对变换，静态历史沿用当前变换和零上一帧几何地址的原有规则。没有冻结相机或对象动画。
- 快照持有不可变发布资源，不靠可变 `Chunk1` 保活。旧快照由现有帧完成与退休机制持有；没有增加全局 idle、提前销毁或取消 GPU 完成检查。
- 仍逐帧批量复制 CPU 表、上传 GPU 元数据、组织 TLAS 和 SBT；不是 GPU 常驻场景表，也没有消除所有随有效几何增长的工作。加载期间发布变化仍可能重建整份有效静态快照。

区块发布链的直接调用方覆盖 GPU 批次完成、等待完成、空批次、重要提交、删除/重定位、世界退出及发光收集关闭。空区段不进入有效集合，槽位容量不再决定普通静态表组织的遍历范围。资源驻留普查改为独立计时，保留每 30 帧的原采样频率，没有关闭诊断来制造收益。

### 32 视距与未覆盖长停顿

候选进程 72120 首次在 83.474 秒达到 17,427 个主区段，86.511 秒起持续平静，取得 659 帧、28.497 秒平静样本。真实帧间隔均值 / p95 / p99 为 43.19 / 52.63 / 62.01 ms；区块组织为 2.608 ms/帧，容量准备为 0.482 ms/帧。快照覆盖 30,617 条几何、13,868,948 字节 CPU vector 存储，平静期重建计数为 0。平均 TLAS 实例约 18,053.3，区块 GPU 缓冲统计为 7,250,285,744 字节。

参考进程 66912 在 16:25:37.557 至 16:27:16.070（本地时间）没有逐秒进展，最终只有 8,618 个主区段。计划 115 秒的停止请求直到 157.098 秒才能处理。未触发观察器的强制终止，之后各维度保存、场景释放、SDK 禁用和正常设备关闭成功；没有设备丢失、崩溃报告、GPU 转储或本组时间范围内的系统 `nvlddmkm` / `Display` 事件。

JFR 在停顿期间的两次线程转储及 784 个 NativeMethodSample 将渲染线程定位到 `RendererProxy.acquireContextNative`。停顿内记录的 GC 暂停约 8 ms，不能解释约 98 秒空白；尚不能区分其中的交换链 acquire、fence、资源退休或其他原生等待，也不能归因为驱动、硬件、窗口状态或本次静态组织。CPU 调用位置不是 GPU 已执行位置，没有新 GPU 故障数据来定因。

原始帧 CSV 只累计约 57.94 秒间隔；在 1036 至 1041 帧的事件跨度内，有 98.243 秒未写入。原分析器因保存、关闭和 CSV flush 完整而接受运行，但这只证明生命周期完成，不证明性能覆盖完整。现已分别输出 `completed_run` 与 `performance_measurement_complete`；有超过一秒的缺失间隔时默认拒绝，`--partial` 明确保留部分数据。

本轮原始分析文件保留不改，新增 `measurement-coverage.json` 将参考 32 标为性能覆盖不完整。不得将该轮已写入帧的 55.77 ms 均值说成整段运行均值，也不将候选完整稳态与参考的加载部分做百分比对比。上一组 80 ms 稳态属于旧进程，不补作本轮参考。

### 环境与证据限制

使用者允许其他程序占用，但实际波动超过轻微程度：参考 16 的整卡显存峰值约 15.08 GiB，候选 16 约 10.51 GiB，同时可用物理内存明显变化；这些不是 Radiance 单进程统计。四轮全机 CPU 均值约 40.8% / 42.7% / 43.1% / 49.6%。

因此记录帧耗时下降和静态 CPU 工作减少的事实，不承诺同等整帧提速百分比，也不把显存峰值差当作本次节省。加载时间还受顺序执行、文件缓存、正常实体模拟和外部负载影响，单样本不足以建立可重复吞吐结论。GPU 主队列时间与 CPU 重叠，不能直接相加，也不覆盖独立区块队列或 SDK 自有工作。

两种路径都有相同的 5 条 Veil 顶点布局拒绝报告，不是快照引入的新差异；本轮不把它改写为完整 Veil 渲染等价或视觉通过。没有实际放挖、移动路线、Advanced 或长期稳定性验收。

## 结论

保留本轮变化驱动的静态快照：产品接缝测试和实际静态计数支持其消除重复组织，16 视距 CPU 自身耗时取得明确下降，候选 32 视距完成完整加载和有界平静窗口。代价是额外 CPU 表存储，以及发布改变时仍会重建快照；逐帧上传、TLAS、SBT 与动态输入尚存。

32 视距参考没有有效稳态且测量漏计长停顿，整帧净收益、可靠加载吞吐和长期表现未闭合。未自动重跑；长停顿与设备丢失保持独立边界，动态几何优化留待后续，不在本轮扩大实现。
