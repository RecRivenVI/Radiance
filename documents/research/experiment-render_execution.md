# Native 渲染执行与性能对照

2026-11-07，149 号连续改进。从保留全部四项介质修复的 C6 出发，分别判断执行组织、着色器、内存与场景构建的改动。

## 问题

重放器在同配置下有约 9%～10% 的窗口差异。原游戏主提交让整个离屏批次等待交换链图像，并以图像索引选择录制槽位。需要分别测量着色与等待，验证拆批和槽位解耦是否保持提交、资源退休及呈现行为。

## 方法

冻结基线为本体 `ad5d465` 加 147／148 开发成果、Extra `953ed9d`。实测游戏 JAR 和 Extra 来自既有场景快照的 `inputs/`，当前源码增量与每阶段构件身份单列。城市固定 2560×1440、32 视距、RR Balanced、四次反弹、FG 关闭。保留地图、材质包和模组组态。取真实游戏帧间隔，分段 GPU 与主机耗时另用 TIMED 窗口。

预算为开工基线一次、呈现与槽位改动分别一次城市运行，独立重放复用单一城市快照。只有异常、明显波动或影响验证范围的改动追加运行。每阶段按正确性与可测成本判定是否保留。全局故障立即停，进程局部故障修复后重启累计上限十次。

## 发现

### 测量校准

148 同配置重放 A1 的四个 120 帧子窗口中，世界 PT 为 21.81、22.83、23.87、25.05 ms。主队列跨度随之从 26.08 升到 29.99 ms。A2 前后走势不同。着色本身存在漂移，不能把总跨度变化全部归到 CPU 呈现等待，也未据此确定着色漂移的硬件原因。重放复用现有采样回调记录 acquire、fence、提交、present 和限帧耗时，按实际帧号对齐。

开工游戏基线 `execution149-a-r32-1440-20261107-151100` 正常退出。FRAME_ONLY 均值／P99 为 26.68／31.79 ms。TIMED 世界 PT、RR、主队列均值为 19.93、2.27、25.95 ms。CPU acquire、槽位 fence 和 `vkQueuePresentKHR` 均值为 0.0048、0.0017、0.0695 ms。上述三项 CPU 计时仅表示对应 API 调用跨度。游戏采样在 `validations/performance-scene_replay/result/` 下，复用 148 的地图与快照。

### 第一阶段：分开交换链拷贝

离屏上传、世界、UI、合成仍按原顺序提交。最终拷贝和图像转换在第二批次等待获取信号，同一个 `vkQueueSubmit` 和 fence 覆盖两批。前后图像内存屏障保留，失败不登记已提交序号。离屏读回沿用其独立提交。

`execution149-stage1-r32-1440-20261107-152024` 正常保存退出，城市画面中的玻璃、装置、HUD 和颜色与基线对应。真实帧间隔均值／P99 为 27.59／34.38 ms，TIMED 主世界 PT／RR／主队列为 20.97／2.27／26.72 ms。CPU acquire、槽位 fence 和 present 为 0.0051、0.0018、0.0549 ms。交换链拷贝均值 0.025 ms。单次帧均值增加 3.4%，世界 PT 差值也落在既有漂移范围，没有取得提速证据。结构改动保留并继续。源码及构件身份分别为 `execution149-stage1-sources.zip` 与 `retire-execution149-stage1.json`。

### 第二阶段：录制槽位与图像索引独立

三个录制槽位按顺序轮转，槽位 fence 证明该次录制与拷贝已完成；呈现信号量由实际取得的图像索引选择。窗口重建按实际尺寸、输出编码与世界管线变化更新对应资源。只有图像数变化时继续使用离屏资源，SDK 呈现历史单独失效。截图只登记已成功提交的录制槽位。

`execution149-stage2-r32-1440-20261107-153129` 正常保存退出。相对第一阶段，真实帧间隔均值／P99 为 27.59／34.38 → 27.37／34.49 ms，世界 PT 20.97 → 20.64 ms，主队列 26.72 → 26.41 ms。槽位 fence 均值均约 0.0018 ms。TIMED 窗口进程工作集样本中位数 6.80 → 7.63 GiB，专用显存样本均约 6.42 GiB，实际间隔未体现更深排队收益。工作集差异尚无归因。画面中的玻璃、装置及 HUD 正常。结构改动保留并继续，窗口重建、HDR、FG 与离屏专项在后续合并核对。

### 第三阶段：设备能力与附件检查

选卡与创建设备共用扩展及 feature 查询，选卡拒绝缺失的核心能力并继续检查其他候选。NGX 三种模式分别报告依赖状态，输出能力仍由显示表面和 SDK 运行时决定。Framebuffer 创建时使用实际视图的格式、用途与 mip 尺寸校验，离屏绑定使用已有物理设备属性。

首次启动正常创建设备，随后检查发现蜘蛛全屏效果将 RGBA8 图解图像附到 RGBA16F 通道。已有动态效果暂存也有同类错配。让两种实际格式分别使用兼容通道和管线，继续复用原图像。记录 `execution149-stage3-r32-1440-20261107-154212` 保留了完整异常、能力和构件身份。修复后的启动使用了 1 次进程内故障恢复额度，未出现设备丢失。

修复后 `execution149-stage3-corrected-r32-1440-20261107-154738` 正常入城、重载、保存退出。截图中的玻璃、装置和 HUD 与阶段二相符。相对阶段二，真实帧间隔均值／P99 为 27.37／34.49 → 27.26／33.35 ms，TIMED 世界 PT 20.64 → 20.34 ms。进程启动到自动请求打开世界约 49 → 47 秒，含固定预备等待。全程驱动管线创建时间 243 → 246 ms，后者多三个匹配格式的创建请求。没有明显退步，保留并继续。GPU 上 NGX SR／RR／FG 依赖均满足，HDR metadata 扩展存在，所测城市窗口实际以 SDR 呈现。

### 第五阶段：近景光源采样有前置缺口

Advanced 的区段发光表由区段发布端收集，采样位置采用纹理分区切出的三角片，辐射值是颜色、顶点染色与发光的均值。表中的片段标识并未由 Vanilla PT 的最终命中发光消费，表的发布也不覆盖普通实体、方块实体、粒子与移动空间姿态。坐标打包当前在绝对世界 float 下做加法，不能直接扩用到大坐标动态来源。

Vanilla PT 通过真实命中累计材质、表面及叠层发光。LoD 主动采样已按近远所有权过滤，并在命中侧按 PDF 给同一贡献加权；程序薄层另有自己的采样路径。将 Advanced 的平均面辐射和近似阴影可见性直接加到 Vanilla 会与真实命中重复，无法用一个常数扣回折射、不同发光纹理及图元侧别。若改为光束引导，仍需在太阳、LoD 和现有命中端使用同一混合 PDF。

目前没有可验证的通用候选，夜景画质与耗时没有可比的 B。保留已有光源路径，独立阶段继续。这个判断基于现有生产表与消费合同的差异，没有用两套算法本身的画质差异冒充主动采样结果。
