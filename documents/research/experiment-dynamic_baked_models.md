# 动态烘焙模型复用与原生提交实验

2026-10-18，按使用者授权先定位城市动态几何生产者，再优化现有烘焙模型持久路径；没有推广到全部 ModelPart、粒子或程序化模型。2160p 只分析既有窗口和分配代码，没有重新运行 4K 压力测试。本记录将生成工作减少、GPU 成本、整帧结果和视觉证明分别处理。

## 问题

当前城市低分辨率仍以 CPU 动态输入为主要候选，但不能继续把所有实体访问都当作顶点生产，也不能假定旧持久模型默认启用。目标是减少同一局部模型反复展开、跨 JNI 传输和动态 BLAS 输入，同时保留 renderer、材质、完整场景、姿态、历史和实际 GPU 完成后的退休。

## 方法

### 生产者归因与资格

先对旧产品开启已有 `ProducerCensus`，取得 PID 116968 的 1,197 帧。该窗口只作归因，不与正式 A/B 比耗时；嵌套 `::item-model`、`::block-model` 行属于父 renderer 的包含范围，不能相加。

| 来源 | 每帧调用 | 每帧实际 PBR 顶点 | 其他证据 |
| --- | ---: | ---: | --- |
| ItemFrameRenderer | 295 | 53,960 | 295 个动态 BLAS 输入；约占全部 PBR 顶点 71% |
| PaintingRenderer | 223 | 13,632 | 223 个动态 BLAS 输入，未走 SimpleBakedModel |
| ChestRenderer | 3,276 次分派 | 2,232 | 只有 31 个实际输入，不能按分派数推算几何量 |
| BedRenderer | 987 次分派 | 1,368 | 只有 19 个实际输入 |
| SpringRenderer | 16 | 1,312 | 程序化变形，保留现有完整捕获 |
| 未归属动态输入 | 不强行分摊 | 约 62.6 | 显式保留归因缺口 |

ItemFrame 的嵌套 SimpleBakedModel 入口分别产生 26,636 和 25,960 顶点，包含时间约 1.290 和 1.063 ms；父 renderer 包含 3.176 ms、自身 0.811 ms，面状态捕获约 2.555 ms。后者仍执行，没有用纹理名、方块名或 renderer 白名单猜测面规则。

旧 `radiance.rigidModels` 默认 false，实际持久实例为 0。已有持久路径只接受普通实体所有者、准确的 PBR consumer、SimpleBakedModel 和合法均匀姿态。BER、粒子、Sprite／glint／outline 包装器、表面附加层和非均匀姿态不因此自动取得资格；模型类相同也不代表最终外观不变。独立的 `radiance.rigidParts` 继续关闭，不重复推广曾增加实例成本的 ModelPart 原型。

### 实现与所有权

本轮产品改动仅在 `RigidModelCapture.java`，配套测试在 `RigidModelCaptureTest.java`。沿用已有 native 持久模型和实例提交接口，没有修改原生产品、shader、场景总表或 AS 算法。

- 渲染器、模型和 tint 回调仍每帧执行。Recorder 对每次原始 quad 调用精确比较局部顶点、面方向、颜色、亮度、light、overlay 和已有颜色模式；不先展开完整变换顶点再 hash。
- 同一 recipe 命中时直接使用不可变快照，不再克隆 BakedQuad、数组和整份 recipe；姿态仍逐实例提交。源数组变化、流长度变化或外观变化会产生独立快照，不冻结动画。
- 第一次分歧只物化已匹配前缀。遇到不支持调用时，先按原顺序重放前缀，再执行原调用，避免丢失混合消费者输出。
- 最近 recipe 索引受既有 512 项／32 MiB 缓存约束。到期、淘汰、世界切换和重载同步清除索引；嵌套回调返回后再次确认 entry 仍驻留，不能从已关闭网格取 native 指针。
- 纹理 owner 及代际仍按实际使用路径校验；当前帧使用过的 entry 不被淘汰。原生 BLAS 引用、实例历史、draw ordinal、镜像补偿、在途强引用和完成退休保持原机制，没有全局 idle。

### 同城对照

原城市夹具 `font-owner-comparison.zip` 保留不动。本轮派生 `dynamic-baked-comparison.zip`，SHA-256 为 `468B12B806BB2D705B23C9A123F88439BE00A8E02DAAE2A9062BFB86A4CC0FE5`。206 个文件中仅 `level.dat` 的 `doDaylightCycle`、`doWeatherCycle` 改为 false，其余逐文件相同；初始时间、天气、实体和动画保留，不把自然时间变化混入两组光照差异。

每次恢复同一夹具及设置，32 视距／模拟距离、Vanilla PT、RR Balanced、Reflex 2、FG 关闭、SHARC 开启、区块发光收集关闭、VSync 关闭。固定原相机，静音，保持相同无边框和聊天屏幕；逐帧核对真实 1920×1080／2560×1440。预热至少 60 秒且 Java／native 队列平静 10 秒，再采样 60 秒，最后 F3+T、字体检查、保存及正常关闭。

两组使用同一冻结 JAR，通过 `-Dradiance.rigidModels=false/true` 选择既有完整输入或新路径；正式窗口关闭重型生产者归因及双路径几何比较。1080p 先参考后候选，1440p 反向；生成帧为 0。世界 tick 继续推进，并非逐 tick 完全相同输入。其他程序可能小幅使用 GPU；没有硬件计数器或完整进程驻留时间线，不能由整卡遥测直接排除渲染成本转移。

开关对照测量的是“限定烘焙复用加 warm recipe 优化”的完整组合，没有单独消融 recipe 克隆本身的收益；原生持久模型能力是已有实现，不重新计为本轮开发成果。

证据根为 `validations/performance-scene_diagnosis/result/dynamic-input-20261018/`；每个 case 保存启动脚本、参数、原始帧表位置、NVML 数据、实际 DLL、设置、日志归档及收据。CPU 包含／自身、Java／native 和嵌套 GPU 区间不能相加。未返回的 GPU 样本不填零。

## 发现

### 工作量与代价

1080p 正式窗口中，动态 PBR 生产均值从 75,618.7 降为 23,069.9 顶点／帧，逻辑输入从 9,679,194 降为 2,952,943 字节／帧，约减少 69.5%；这不是 PCIe 实际传输字节。复用侧每帧引用 52,548 个局部顶点、494 个实例、147 个驻留模型。动态 BLAS 输入由 609 降为 407，静态几何仍为 31,559，TLAS 实例由 18,482 增为 18,774。

正式窗口未观察到新的持久模型上传／构建事件，表示预热后的模型被复用，不表示首次进入或重载不构建。实例数增加 292 是实际成本，不能只报减少顶点。绘画、动态弹簧和其他不满足合同的来源仍每帧完整生产。

### 正式窗口结果

| 窗口与执行顺序 | 帧数 | 整帧均值 ms | p95 ms | p99 ms | 渲染线程 CPU ms | 主队列 GPU ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1080p 参考，先运行 | 1,658 | 36.202 | 44.870 | 53.357 | 35.717 | 16.364 |
| 1080p 候选，后运行 | 1,799 | 33.354 | 44.100 | 52.839 | 32.457 | 22.754 |
| 1440p 候选，先运行 | 1,652 | 36.333 | 50.900 | 61.973 | 34.409 | 33.098 |
| 1440p 参考，后运行 | 1,256 | 47.794 | 64.649 | 76.363 | 43.491 | 42.484 |
| 1080p 参考，收尾复核 | 1,566 | 38.336 | 51.437 | 62.350 | 38.015 | 20.536 |

1080p 的帧间隔均值观察下降约 7.9%，换算真实 FPS 约 27.62→29.98；1440p 约 20.92→27.52。每个值是一份 60 秒窗口，间隔首行未定义而省略，所以间隔样本比帧数少 1。没有把逐帧样本当作上千次独立实验，也没有以单对窗口确定跨运行置信度。

由于第一组 GPU 区间增加，结束 1440p 后另跑一次相同夹具的 1080p 完整输入参考，不改产品、不扩大矩阵。参考 GPU 从 16.364 变为 20.536 ms、整帧从 36.202 变为 38.336 ms，说明参考本身也有运行间波动；候选的均值低于两份参考，但不能据此排除其 GPU 成本。复核没有设备丢失，按同样方式完成重载和关闭，不追加重复运行。

1080p 中 `GEOMETRY_MARSHAL` 自身 4.359→2.274 ms，native `pt.prepare.blas-record` 自身 2.284→1.502 ms；Java 提交／呈现自身 11.028→10.653 ms，并非全是等待。native 与 Java 的包含关系仍重叠，不能相加成独占收益。

GPU 成本有取舍：1080p 实体 BLAS 0.925→0.791 ms、上传 0.483→0.186 ms，但 TLAS 0.242→0.382 ms；1440p TLAS 0.309→0.434 ms。多实例确实增加顶层工作，未被 CPU 节省抹去。

世界 PT 在 1080p 为 11.889→17.899 ms，而反向运行的 1440p 为 34.348→26.655 ms，方向不一致。DLSS／SHARC 等阶段也随窗口变化，图形频率均为 2,790 MHz；整卡占用、驻留与 GPU 排队尚不能按进程完整分解，因此不能认定新路径必然增加或降低 PT 遍历耗时，也不能直接把 1440p 约 24% 的整帧下降全部归因于复用。

1440p 的整卡显存均值约 15,280／15,524 MiB、峰值 15,478／15,718 MiB，两个流程均无 SDK 显存预算告警。它们不是进程资源峰值，不能宣称本轮减少了对应数量的应用显存；4K 的历史预算问题仍单独保留。

### 自动回归与游戏内边界

Recorder 的 13 项测试覆盖 warm recipe 不展开／不克隆、源数组变化、前缀分歧、增加／删除／空流、回退顺序、颜色／light／overlay 变化、姿态快照、非均匀／镜像变换与历史身份。另执行 PartModelCapture 6 项；不是只检查缓存类字段或源码字符串。

隔离生命周期进程 PID 106752 完成共享模型、不同姿态／颜色、玻璃裁切、glint／轮廓回退、空输出、纹理／模型重载、对象替换及 F3+A 的 8 个阶段并 PASS。末阶段共比较 1,357 次 draw、143,668 顶点、147 个模型，局部几何与按姿态展开参考的位置／法线误差为 0。该探针属于 CPU 输入一致性检查，不代替完整 GPU 命中或使用者视觉验收；其附带的非完整 profile 不作性能窗口。

原生 `mcvr.rigid-model-gpu`、`mcvr.rigid-build-lifecycle`、`mcvr.rigid-instances` 实际执行 3/3 通过。首次直接 CTest 因缓存使用 R: 路径而没有执行；确认映射指向本仓库后重测通过并解除映射，不把首次失败隐藏为通过。

完整检查通过：GAME 319、line JNI 4、probe 34，bootstrap 11 通过／2 跳过，非 GPU CTest 71/71、collector 2/2；发行结构核对 154 个必需成员且不含探针，严格合规零失败／零警告。首次完整检查发现基线 JAR 错放验证结果目录，已移到生成目录 `build/dynamic-input-20261018/baseline.jar` 再重测，没有放宽 G-09／V-04。

### 2160p 显存来源盘点

只读取前轮 `resolution-sweep-20261018/res2160c`，没有启动 2160p。该旧流程有 358 条 SDK 显存预算告警，进程单点 dedicated 约 11.74 GiB、shared 约 1.49 GiB；不能据此独立证明分页、泄漏或设备丢失。

后五行是源码逻辑估算：假设 3 个在途槽位，按各资源实际 trace／output 尺寸、格式、层数和 shared 配置计算，不能当作测得的总物理显存。未包含对齐、mip、VMA 块余量和 SDK／驱动私有分配，不把已有 input/output 引用再算一份。

旧 2160p 窗口的部分已跟踪 buffer 约 7.42 GiB，包含场景表、几何、AS 等混合资源，不能全部标为区块；image 约 3.15 GiB。collector 在 SERVICE 之后挂接，按 kind 的累计值漏掉更早分配；VMA 总字节又包含 host-visible，二者都不能直接等同 WDDM dedicated 驻留。

源码确认 `ShaderPack::initRuntimeTextures()` 对 pack 声明纹理分配资源，部分效果 pass 未启用仍有中间纹理；多槽 UI／PT／升频输出也随像素增长。它们是后续精简资源资格的候选，不在本轮直接删减。SDK 私有分配、预算、碎片和逐进程驻留仍未完整归因；没有用减少几何、调低画质或提前销毁在途资源掩盖预算问题。

## 结论

生产者归因支持保留限定资格的通用烘焙复用，默认启用该路径而继续关闭 ModelPart；不预先推广全部骨骼或重写 PaintingRenderer。重复 PBR 顶点及动态 BLAS 输入已实际减少，当前城市两档正式对照均观察到整帧均值下降，但增加 TLAS 成本且 GPU 区间未完全归因；暂不扩大覆盖，也不把单轮约 8%／24% 的整帧差值宣称为普遍收益。1080p 的 p95／p99 仅小幅变化，最大间隔反而更大，不能写成所有长帧已修复。

完整视觉等价、运动相机性能、更多第三方模型、长期稳定性、设备丢失根因及公开二进制许可仍未闭合。不由本轮 CPU 减负承诺真实 60／120 FPS，也不自动扩大到下一条动态路径。
