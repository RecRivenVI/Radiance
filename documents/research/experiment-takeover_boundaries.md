# 完整接管的提交、地形与呈现边界实验

2026-10-19，在先前独立接管实验的工作区上执行四项最小功能核对。结果支持继续建设独立提交骨架，但没有证明全部来源程序和严格的“FG 仅处理世界、完全不处理 GUI”已经可用；本轮没有产品代码或 shader 修改，没有性能测试、Prism 操作、提交或推送。

## 问题

正式工程前需排除四类架构假设：DLSS 是否允许完全独立的 GUI 呈现；复杂表面与目标依赖是否能保留；共享模型的不同用户能否独立变化；地形更新能否按完成后的版本发布。小夹具只能证明具体机制，不能代替所有来源清单或生成帧动态验收。

## 方法

使用[接管边界验证](../../validations/conformance-boundaries/validation.md)，固定 1920×1080、静音、8 视距的小型自有世界。仅加载 Minecraft、NeoForge、Radiance 和探针，不加载 Flywheel。世界采用现有 Vanilla PT／NRD／FSR 预设；FG 阶段只启用 DLSS FG，SR／RR 没有同时更换。保留输入隔离、不抢焦点与 Aftermath 基础采集，不启用性能计时或重型验证。

探针在既有独立桥中先共享一个局部模型给红／绿实例；随后只给绿色实例提交变形后的新不可变模型资源，红色实例继续引用原资源，再删除替换并重载。它是资源版本替换实验，不是 GPU 参数形变实现；不能原地修改共享资源，再依靠“同一个类”推断其他实例不受影响。

屏幕中实际绘制分数 alpha 面板与文字、GUI 物品，再执行局部反色、背景模糊和后续清晰 UI；世界相机在 FG 窗口内按探针轨迹运动。通过现有呈现所有者缓存的 SDK 计数观察是否真的生成帧，没有增加第二个 `slDLSSGGetState` 调用方。原版眼睛来源状态、异常恢复与附加层政策执行实际合同断言；两个离屏附件的写入→采样→再混合在重载前后进行 GPU 像素读回。夹具也包含眼睛和充能苦力怕，但未对每个源层的最终像素建立独立断言。

地形在 x=15／16 的区段边界快速交替修改方块与水，最终固定为红色混凝土与水；附加区段回调向全空气区段提交真实网格。原生有界跟踪关联 GPU 完成、发布、场景记录及对应提交完成的帧；Java／native 时钟通过同次读取两侧括号保存，不直接相减。

源码与证据位置在验证的 `result/`：`source-runtime.json` 记录 2,084 个非生成源文件的原始字节哈希及 14 个 gitlink，`source-runtime-02.zip` 逐条读回校验；`loaded-modules.json` 从实际进程模块表取得 core、Streamline 和 Aftermath 路径／哈希。原生 core 为 `B023613AE93F98B4D54433ADB97D78D50DB1A380D4F8403F83FBE580F30A712C`，与此前实验一致。完整工作区仍是 HEAD 加未提交改动，不能仅用 HEAD 标识。

首次启动因验证目录过长，Windows 文件打开失败于 `spider_blur_main_h15_frag.spv`，未进入世界，无设备丢失。缩短新增验证目录后完成客户端流程；失败日志独立保存在 `result/failed-startup-01/`。首次源码归档误包含正在变化的生成跟踪，校验失败；没有用于源码身份，纠正为排除全部生成目录并逐条校验的新归档。

## 发现

### DLSS：真实帧输入通过，生成帧尚未验证

当前固定 Streamline 为 2.14.1。依据其[官方集成指南](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.1/docs/ProgrammingGuideDLSS_G.md)，UI Recomposition 会分别插值 HUD 和场景后合成；它不是“GUI 完全绕过 FG”的保证。对应头文件只暴露错误回调，没有已核实的生成帧后任意 GUI 绘制回调；当前 Vulkan 呈现由 Streamline 异步拦截。没有证据支持直接在 `vkQueuePresentKHR` 后补画即可正确控制生成帧、节奏和资源寿命。

本次 SDK 可用，FG 开关与输入路径确实执行；18 次观察的生成计数全部为零，**生成帧动态实验未通过**。探针记录的 18 次“focused”是 Minecraft 的游戏标志，不是 GLFW／操作系统实际焦点；不能据此排除失焦，也不能断言零生成只由失焦造成。没有自动再次启动来凑取非零结果。

真实帧捕获包含完整 1920×1080 final、HUD-less 和 R32 float UI alpha。原生完成标记到达；2,073,600 个像素中，79,302 个为分数覆盖率，22,354 个为完全覆盖。UI alpha 与 final alpha 的最大绝对误差为 `2.97e-8`；零覆盖区域 final 与 HUD-less 的 RGB 最大差为 2/255。捕获记录实际经过 1 次背景仿射操作与 6 个加权模糊 pass，不代表生成帧动态结果。

现有后端会为背景依赖效果调整 HUD-less 输入；新架构必须分别定义世界结果、屏幕效果和最终呈现。先把请求和资源分开是可行的，但不能因此宣称标准 SDK 已满足所有严格分离要求。

### 表面与作用域：具体路径成立，任意程序未获证明

来源状态事务、JNI 颜色、已封口批次、眼睛层与名称牌发光政策断言通过。重载前后真实离屏 GPU 读回均符合 `(127,0,128)`／`(191,64,0)`，通道容差 2。截图保留了 GUI 物品、前后 UI 顺序、模糊和反色的实际输出。

这证明当前示例所需的状态、附件依赖和层处理可由 Radiance 拥有，不能证明任意世界 shader、导数、屏幕采样、Veil 程序或全部 cutout／动态 UV 与 GUI 3D 最终视觉已经一比一等价。相关 GPU 材质／覆盖合同另执行，但与新公共接口尚未实现的状态分开。

### 实例：可复用资源版本，不冻结单个对象变化

初始两实例共享模型 1；绿色实例替换为新模型 6 后，红色实例仍引用模型 1。重载后的模型取得新身份。两次截图的受控区域均保留超过一万个红／绿像素；数据合同与最终可见面共同构成基本隔离证据，不以像素数量相近证明所有位置、法线或历史逐像素等价。

该结果支持“资源＋独立实例＋显式变化”的基础能力。单对象真正形变可先发布独立网格版本，后续再做参数形变；不能把本次版本替换描述为共享顶点原地写入安全或 GPU 形变已经实现。

### 地形：完成后发布的现有路径可复用

额外区段 renderer 实际执行 7 次；边界最终方块和水状态到达客户端。跟踪无丢弃，关联到 1,762 条 GPU 完成→版本发布→场景记录→完成帧链，其中 462 条 revision 大于 1；这些包含初次加载与重载，不全部归因于边界那两格。

这比“Java 编译结束／JNI 返回”更接近实际执行证据，但没有逐像素证明每个边界方块的首个显示帧，也未在本次强制制造一个过时代际完成竞争。过时代际与资源退休仍由现有针对性合同回归，不能称为本次真实客户端故障注入。地形应使用持久区段版本及增量更新，不能以相机可见性删除 PT 所需几何。

## 结论

独立核心、持久资源／实例、GUI／离屏依赖和地形完成发布具备可复用接缝，足以推进正式阶段 0／1，不需要以 Flywheel 为核心，也不必先重写全部后端。地形与动态模型共用身份、revision、场景边界及退休合同，但保持各自适合的更新粒度。

当前不能承诺严格的“生成帧完成后再独立绘制全部 GUI”：标准 Recomposition 仍处理 UI，本次也没有实际生成帧证据。应将严格呈现分离保持为独立未闭合项；先落实世界／屏幕输入所有权，不把未经证明的 post-FG 回调写入公共接口。任意表面程序和源层完整等价仍由后续双轴覆盖逐项核销，不缩减全面接管目标。

本轮客户端正常保存全部维度并完成 native 关闭，无设备丢失、无 GPU 转储；不构成长时间稳定性或历史故障根因证明。运行证据按 ZIP Deflate、逐条 SHA-256 校验后保存，复制客户端与无效首版归档已进入 Windows 回收站，外部实例未操作。
