# 巨大子世界缺失与组合场景 CPU 帧时间调查

2026-10-25，129 号在使用者正常保存退出后的 Prism 配置、模组与 Newport City 副本中复现并修复巨大 Sable 结构缺失；随后保留实际 GPU 路径，采集加载、站立与移动窗口。本记录不把使用者观察的 25～30 FPS 当作严格基线，也不宣称其他正确性项目全部通过。

## 问题

使用者在 128 配对包中加入巨大 Sable sublevel 后，结构没有显示；同时希望知道 4K、32 视距城市里 CPU 与提交链仍在处理什么。优先保证完整内容，再解释性能；没有通过少画结构、降低画质或关闭 GPU 功能取得结论。

## 方法

源实例为 `E:/Minecraft/PrismLauncherDev/instances/Radiance 1.21.1-neoforge`。只读检查日志中 13:39:29 完成各维度保存、13:39:31 停止后，按实例锁协议冻结配置、模组清单和完整 Newport City；未操作、启动或替换 Prism。338 个文件的读取前后大小、时间与 SHA-256 一致，ZIP 逐条读回校验通过。来源清单为 `validations/conformance-takeover/result/platform-sublevel/source.json`，输入明细在其链接的夹具清单中。

实际组合是 NeoForge 21.1.264、Java 21.0.11、Create 6.0.10、Sable 2.0.6、航空学组合 1.3.2、Custom Skin Loader 15.1 和 Zume 1.2.2；内嵌 Flywheel、Ponder、Veil 等随父包，不另行升级。没有 Voxy。原 128 本体／Extra 哈希与源实例相符。测试只从登记的不可变输入复用相同字节，不从可写 Prism 目录链接运行。

## 发现

### 空区段误判与调度饥饿

目标 UUID 为 `92b605ec-6b0c-4d32-9247-97077accbc65`，约 293×175×113 方块，客户端和服务器均有 34 个 sublevel。目标采用正确的 Sable 区段 renderer，665 个区段已登记；存档中 422 个区段有内容，243 个为空。原包持续为 665 dirty、0 native-ready。不是没有收到结构，也不是 GPU 可见性或尺寸上限。

实际 NeoForge 264 的 `RenderRegionCache.createRegion(..., checkEmpty=true)` 对已知空区段返回 null。本体外部区段准备却把它当作来源未到达而反复延期。调度又按 `ConcurrentHashMap` 迭代，每帧最多尝试八项，延期项留在固定迭代位置。存档、Sable 网格顺序和实际 Native ID 复算表明，前八个桶全部为空，第一项有效几何排在它们后面。推导与运行记录一致，明细见基线用例的 `deferred-grid-proof.json`。

修复分两处：

1. 准备前独立检查来源区块确实存在；已知空区段不再触发 `checkEmpty` 捷径，而是沿原 worker、版本与零几何完成路径正常处理。真正未到达的数据仍延期，保留旧几何。
2. 最新票据表保留，增加去重轮转队列；延期／运行中项回到尾部，同一轮不反复尝试同一项，容量预算不变。保留代际、来源身份、失败归还、GPU 完成后发布和资源退休。

修复后两次均为 dirty 0、native-ready 422，与存档有内容区段数相符；不是要求空区段也拥有 BLAS。1080p 在首份快照后约 24.4 秒、4K 约 27.6 秒观察到全部 422 项就绪，这只是周期快照的观测时刻，不是首个使用新几何的精确延迟。1080p 同角度截图明确从缺失变为大石质结构实际可见，4K 后续截图仍包含结构和城市。原始截图与保存／关闭日志在各用例的证据归档中；计数和截图均不替代使用者全面目视验收。

### 4K 的一帧分布

三窗均无 writer／Native 丢弃、帧 token 缺口、失败帧或 GPU omission，CPU 样本标记有效。加载窗 521 帧，站立 334 帧，移动 263 帧；站立开始时 Java 列／重建队列及 Native 构建队列已为零，其后有零星正常更新；移动重新触发加载。

| 窗口 | 平均帧间隔 | p50 / p95 / p99 | 渲染线程 CPU 平均 | GPU 世界通道平均 |
| --- | --- | --- | --- | --- |
| 进入世界后前 20 秒 | 38.44 ms | 34.75 / 67.07 / 94.22 ms | 33.14 ms | 27.15 ms |
| 站立 12 秒 | 35.98 ms | 35.77 / 38.02 / 39.34 ms | 23.34 ms | 34.56 ms |
| 移动 12 秒 | 45.68 ms | 45.44 / 58.69 / 61.67 ms | 33.80 ms | 42.51 ms |

加载窗有 54 个超过 50 ms 的间隔、4 个超过 100 ms，最大 546 ms；站立只有 1 个超过 50 ms，最大 68.92 ms；移动有 40 个超过 50 ms，最大 73.16 ms。GPU 主 PT 子通道均值分别 20.08、26.80、34.13 ms，属于世界通道内部，不能再次累加。TIMED 与 JFR 是带开销的归因窗口，不是关闭探针的正式 FPS 跑分；未额外控制其他程序的小幅负载，不作收益百分比或理论上限承诺。

### 非 GPU 工作与等待

| CPU 墙钟阶段，按记录帧数归一化 | 加载 | 站立 | 移动 | 含义 |
| --- | --- | --- | --- | --- |
| 实体 self | 4.76 ms | 3.05 ms | 3.54 ms | 不含拆出的材质等子阶段 |
| 方块实体 self | 1.46 ms | 1.85 ms | 2.17 ms | 另有 Sable 来源回调 |
| 面状态 setup／restore／capture／clear self 合计 | 5.50 ms | 4.03 ms | 5.76 ms | 跨生产者的真实捕获与状态处理，不能全删除 |
| Native 提交／呈现入口 | 6.81 ms | 6.13 ms | 10.65 ms | 含场景准备及同步，不等于纯计算 |
| FRAME_OTHER self | 5.48 ms | 12.79 ms | 11.74 ms | 未归类段，包含节拍／等待 |

站立渲染线程 JFR 共 137 个执行／Native 样本，25 个叶子在 `streamlineFrameEvent`；调用路径是 `RenderSystem.flipFrame → prepareNextInputFrame`，Native event 0 调用 `beginFrame → slReflexSleep`，实际配置 Reflex 2。结合线程 CPU 与 GPU 时长，FRAME_OTHER 不能按 12.79 ms 全归为忙计算。JFR 没有捕获该线程的 Java monitor／park 阈值事件，也没有完整 C++ 等待栈；因此不能精确断言其中全部都是 Reflex sleep，更不能据此关闭 Reflex 或 VSync。

站立另有 11 个叶子样本落在 `AbstractCollection.addAll → SableSubLevelBridge.collectBlockEntities`，8 个落在 `Class.privateGetDeclaredMethods → getMethod → SableSubLevelBridge.invoke/readPose`。源码确实每帧遍历各子世界的已加载区块、建立身份集合收集 BER，再重复查询姿态访问方法；公共区段同步也每帧走全部外部区段。它们是具体的重复求值候选，但少量样本的占比不是毫秒预算。实体捕获内也出现局部部件状态整理和 Native 提交；日志确认 Sable、Veil 的未登记修改使部分原版入口退回 CAPTURE，不能把混合模组场景当成全直接接管。

站立 Native 内部的静态实例追加 0.99 ms、元数据选择 0.67 ms、TLAS 命令准备 0.78 ms、外部元数据 0.33 ms；这些包含在上述提交入口。移动时 SBT 分配／复制／记录升至 1.74 ms，区块顶点打包 0.73 ms；新加载内容可能合法改变 SBT 布局，现有证据不足以直接宣布缓存失效有错。加载时顶点打包 1.12 ms、批次构建命令 0.99 ms，不代表 CPU 所有区块任务的关键路径总耗时。

JFR 加载窗 GC 停顿合计 381.47 ms、最大 22.74 ms；站立 15.53 ms／最大 4.05 ms，移动 49.10 ms／最大 6.66 ms。它解释加载期的一部分波动，但不能解释唯一 546 ms 长帧的全部成因。生物群系查询样本对应原版客户端 `animateTick`，属于保留游戏效果的必要工作，不应直接删掉。

## 结论

巨大结构已从来源接收、调度、构建与 Native-ready 到实际截图显示完成验证；修复没有删除结构、改变坐标或放宽 GPU 发布条件。唯一候选身份为 `validations/conformance-takeover/result/platform-sublevel/candidate.json`，原 127／128 包与证据保留，129 尚未投放 Prism，也未提交／推送。

下一项 CPU 优化建议是聚焦组合场景的动态输入与 Sable 来源准备：先分清姿态访问、BER 成员集合、实际 renderer 和面状态处理，复用已解析访问器；只在生命周期可靠通知下增量维护成员集合，并使同一帧同一姿态求值尽量共用。当前姿态、回调、光照和变化仍须执行，不缓存上一帧最终几何，不直接放行未知 Mixin。预期改善 CPU 提交与实体密集／大结构下的长帧，不承诺 4K 整帧按局部节省同步增长。

次选才是核实 Native 静态追加／元数据及移动 SBT 的实际变化率，再决定是否进一步增量化。4K 世界 GPU 已占约 35～43 ms，CPU 优化有价值，但单靠它不能从本轮证据推出真实 60 FPS。本轮只给建议，不自动实施这些后续优化；下蹲异常全部触发条件、启动交接、设置界面、GPU 历史故障和公开许可仍各自未关闭。

所有运行副本在结论取证后回收，保留世界输入、源码快照、文本、截图、JFR、当前候选及既有唯一证据。129 独立获准验证目录临时 5 GiB；缓存清理及最终占用见候选清单，未操作旧 MCVR、Codex 引用、reflog 或其他实例。使用者仍需对巨大结构的完整外观、运动和交互做最终体验验收。
