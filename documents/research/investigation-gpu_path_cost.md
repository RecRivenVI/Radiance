# 世界 PT 路径成本调查

2026-11-01，承接 NVIDIA 专项准备，使用当前配套候选和城市保存点继续调查世界 PT。已经取得透明分裂方式的同进程对照；没有修改产品默认配置、Native 或 Java 渲染逻辑，也没有把本次带外部负载的窗口当作最终提速承诺。

## 问题

初始基线的主世界 PT 约占 GPU 主队列区间的 82%，但整卡吞吐不能说明具体调用为何昂贵。需要先验证水面反射／折射是否产生显著额外工作，并区分路径预算、材质交换、硬件等待和重建成本。使用者允许其他线程的纯原版客户端重叠；记录真实边界，不操作这些客户端。

## 方法

沿用本体 `ca2bde5a…`、Extra `bb98550e…`，不带 Voxy。城市相机约 `(-132.83, 63.25, 165.15)`、yaw `-107.63`、pitch `9.19`，画面下半部以水面和倒影为主。32 视距、2560×1440 输出、1485×835 PT 分派，四次反弹、RR Balanced、SHARC、真实水面和当前资源包，FG 关闭。时间和天气固定，地图、配置及音量在结束后按原始输入的 SHA-256 恢复。

先尝试通过已安装的 Nsight Graphics 2026.3 SDK，从 JVM premain 在 SERVICE 创建 Vulkan 之前初始化，再在城市队列平静后触发八帧／最多 500 ms 的 Shader Profiler。遵守 [SDK 初始化时机](https://docs.nvidia.com/nsight-graphics/UserGuide/sdk.html)，不调用键鼠，不锁 GPU 时钟，不同时开启软件工作量原子计数。

随后在普通客户端内进行 A→B→A 对照：确定性反射／折射双路径、已有的随机分支、回切确定性分支。通过实际设置入口重建，等待 20 秒后分别采集 20 秒 FRAME_ONLY 和七秒 TIMED；逐阶段核对全部实际模块参数、选项和资源包。普通半透明一直保留随机覆盖，不与透明反射／折射分裂方式混淆。截图用于核对画面与点位，不代替动态视觉验收。

工作量观察另用临时算法包，复用已有八个计数槽与完成事件，未扩充 Native ABI。只改变观察语句和算法包显示名，用 `frameIndex` 轮换 16×16 采样相位，不消耗着色随机序列。仅统计查询 pass，SHARC 更新不写这些槽；原始槽名通过随结果保存的 schema 明确映射，不能按旧名字解读。插桩窗口只解释工作，不作为正常帧率。

## 发现

### 确定性分裂是当前水面点位的明确成本候选

| 方式 | FRAME_ONLY 帧间隔均值／p95／p99 | 独立 TIMED 世界 PT | 独立 TIMED GPU 主队列 |
| --- | --- | --- | --- |
| 确定性 A | 32.63／35.83／39.83 ms | 29.27 ms | 35.71 ms |
| 随机 B | 23.93／28.32／32.04 ms | 19.38 ms | 25.86 ms |
| 回切确定性 A2 | 35.59／40.69／47.12 ms | 28.23 ms | 34.37 ms |

本点位的随机方式对应约 41.8 个真实渲染帧／秒，两次确定性为约 30.6 和 28.1。B 的普通帧间隔比两次 A 分别短 26.7% 和 32.8%；这只是本次窗口范围，不是安静环境下已经确认的固定收益。RR 模块仍约 2.60～2.75 ms，主要变化发生在世界 PT，而非重建模块。各 GPU 区间有包含关系，不能相加。

六个窗口均失去前台焦点，未混入 FG，显卡采样时钟保持 2790 MHz。A1 与 B 分别重叠不同的 Mine-Craft-Protocol 客户端；A2 又重叠额外客户端的启动，整卡显存约 11.3～12.0 GiB。A1／A2 普通帧均值相差约 9%，详细计时与普通窗口也有差别，因此不把差值全部精确归因给设置。保留所有窗口，没有剪除不利长帧；方向性结果须结合下述工作量观察判断，不能直接推广到城市任意位置或前台真实 60 FPS。

截图中两种方式均有反射与透射，但随机方式的水面细节、亮反射重建观感不同。水波动画相位也不同，单张图片不能用于计算图像误差；仍须动态观察噪声、模糊、拖影和亮度稳定性。本轮没有替使用者选择新的默认模式。

### 轻量观察确认了真实工作量变化

临时算法包在相同点位再执行一次 A→B→A，仅记录插桩数据，不把其帧率列为收益。三个窗口分别取得 536、696、444 个完整 GPU 计数帧，每帧八个字段全部存在；均覆盖超过一轮 256 相位。每个窗口末尾三个在途帧未返回计数，按缺失处理。没有 profiler 写入丢失、native event 丢失、失败帧或令牌缺口。

| 每个抽样像素的工作 | 确定性 A | 随机 B | 确定性 A2 |
| --- | --- | --- | --- |
| 已计查询 trace 总数 | 5.272 | 4.387 | 5.281 |
| 初始世界／手部查询 | 2.000 | 2.000 | 2.000 |
| 后续 trace | 3.272 | 2.387 | 3.281 |
| 首个透明像素比例 | 44.76% | 44.88% | 44.76% |
| 允许查询中的 SHARC 命中率 | 72.86% | 69.48% | 72.79% |

三个窗口都满足逐帧恒等式“总数＝初始＋后续”，命中不大于查询，透明像素不大于抽样像素。两个确定性窗口的总查询／像素只差约 0.17%，说明工作量观察比受负载影响的帧率稳定。随机方式减少约 16.8～16.9% 的已计 trace，后续 trace 减少约 27%；它不是仅靠改变曝光或重建参数获得更短帧时间。首表面比例接近，未通过去掉水面制造收益。

这些数值不含太阳阴影、any-hit 候选交点、SHARC 更新和 BVH 节点访问，不能称为整帧全部光线数，也不能把查询减少比例直接当作性能提升比例。计数代码、采样相位、旧字段到当前意义的映射及原包 SHA-256 均随结果保留；非插桩对照仍使用原始内置算法包。

本点位没有观察到 raygen 的续接事件，因此没有支持“边界续接循环异常导致这处掉帧”的证据；不能据此排除其他玻璃、水体或叠层场景。SHARC 对允许查询已有约七成命中，也不支持把“缓存根本没有工作”当作此处主因。

另一个明确候选是全屏手部查询：每个抽样像素均执行一次世界查询和一次手部查询，包括图像中没有手部的区域。它约占本次已计查询的五分之一，但 miss 查询可能很便宜，尚未隔离其耗时。值得研究按真实手部投影范围缩小查询范围，保留折射、第一人称所有权和历史；不能直接省略手部或按这五分之一推算 FPS。

### 当前实现中需要继续区分的成本

`world.rgen` 对确定性透明首表面分别准备反射和折射，并各自调用后续追踪。每条路径还可能包含不消耗散射深度的边界续接、阴影查询及缓存查询，四次反弹不能代表固定四次 trace。

`MainRay` 含约 200 字节的逻辑标量分量，介质历史留在 raygen；双分支还要保留来源射线与各自历史。逻辑大小不是硬件寄存器数，源码中看见多份变量也不代表编译后全部同时存活，不能据此直接断言 spill 或 SER 收益。

材质通过 `rayMaterialStateImage` 交换，包含 image 写入、读取与内存屏障。编译器可能消除未使用的分量和读取，不能按源码函数调用次数直接估算显存流量，更不能为了缩减代码删除必要的跨调用可见性。其实际代价仍需源码／IR 关联或独立对照。

区段和持久模型都已根据实体类型和面规则选择 opaque 几何；保留需要 any-hit 的裁切、成像所有权、成对薄片和水体排除规则。不能把“所有区段都没有不透明快速路径”列为现状，也不能通过强制 opaque 破坏这些语义。

### 重型工具未形成可用的逐着色器结论

SDK 初始化与城市触发均返回成功，并写出约 187 MiB 的 `.ngfx-gputrace` 文件；但 `ngfx.exe` 随后在 `Qt6Core.dll` 中以 `0xc0000005` 崩溃，自动导出失败，文件完成性和 Shader Profiler 数据尚未确认。Windows Application 1000／1001、命令和原文件已保留；没有将该次卡住十二秒的工具窗口算入正常性能。

Java 返回码为零，但没有控制器正常停止标记，不能据此宣称该会话正常保存退出。输入已按原档恢复。原生记录有正常设备关闭，没有发现设备丢失；这与 GPU 设备故障分别处理。不自动重复该采集，不以关闭检查或改驱动掩盖工具问题。[官方 Shader Profiler](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html)可提供等待和活跃状态，但本轮尚未取得这些数据，不能补写为已经定位的 stall 原因。

## 结论

透明双路径是值得优先调整的明确成本来源：已有源码、同点位时序对照和独立工作量观察。建议先对透明路径预算与重建进行集中优化，再隔离全屏手部查询的实际成本；材质交换、调用点活跃状态与 SER 仍是后续候选，不能写成已确认根因。没有证明当前场景已经能达到真实 60 FPS。后续补齐阴影及 any-hit 的归因，NRD＋DLSS、移动和缩放分别验证，不为凑覆盖率重复全组合。
