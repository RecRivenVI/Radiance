# 半透明与多光源手工场景的首轮性能采样

2026-10-17，使用者在本轮项目内实例先准备新版半透明卡顿场景，再准备多光源卡顿场景。本记录保存各一轮 60 秒的探针和 JFR 数据，没有性能优化代码或同场景前后 A/B，也未开始高视距专项。

## 问题

普通半透明视觉及加载页淡出分别已获使用者通过，性能尚需分开判断。两种手工场景可能有不同瓶颈，不能把“光源多时慢”直接当作光照采样复杂度的证明，也不能把所有 CPU 等待视为可删除的顶点开销。

## 方法

使用同一开发客户端 PID 46560、1920×1080、12 视距、Vanilla PT、DLSS RR Balanced、4 反弹，FG 关闭、Reflex 1、vsync 开启、帧率限制 260，普通半透明磁盘设置为前景／背景混合。配置文件与 SHA-256 均保存在分析 JSON 中；没有降低视距、质量、关闭模组或改动世界语义。

分别执行 `requestSceneProfile`，场景标签为 `translucency-heavy` 和 `many-lights`、时长 60 秒；控制文件的实际请求身份、开始／结束与写入完成均在启动日志中。附加各一份有界 JFR，以及只读 NVML 板卡显存／负载采样。JFR 和 NVML 与主窗口并非完全同时开始，以各自时间戳取交集，不能将窗口之外的数值填入主样本。

原始数据位于 `validations/performance-scene_diagnosis/result/`：

- 半透明：`profiles/2026-10-17T15-28-29.428285700Z-pid46560/`，15:28:29～15:29:29 UTC，2,435 帧；对应 `translucency-heavy.jfr`、`translucency-heavy-gpu.csv` 和 `translucency-heavy-analysis.json`。
- 多光源：`profiles/2026-10-17T15-32-13.009020900Z-pid46560/`，15:32:13～15:33:13 UTC，1,921 帧；对应 `many-lights.jfr`、`many-lights-gpu.csv` 和 `many-lights-analysis.json`。

本次没有静态世界副本／相机坐标快照；世界由使用者在本项实例中创建和操作，未退出前不复制活跃存档。当前两个窗口均记录 `ChatScreen`，但世界持续渲染；半透明 2,327 帧有焦点，多光源全部失焦。没有生成帧，两份数据是各自现场诊断，不构成严格互比，更不能计算优化收益。其他项目进程存在，板卡总负载不能全归到 Radiance。

## 发现

### 同一轮任务中存在不同瓶颈

| 指标 | 半透明场景 | 多光源场景 |
| --- | --- | --- |
| 真实帧起点间隔均值 | 24.645 ms | 31.200 ms |
| 起点间隔 p50／p95／p99 | 24.158／27.775／30.186 ms | 30.642／36.556／40.104 ms |
| runTick 墙钟均值 | 24.414 ms | 31.092 ms |
| 渲染线程 CPU 均值 | 6.969 ms | 30.811 ms |
| 主队列 GPU 完成区间均值 | 23.800 ms | 9.350 ms |
| PT 模块 GPU 完成区间均值 | 21.890 ms | 6.788 ms |
| RR 模块 GPU 完成区间均值 | 1.579 ms | 1.836 ms |
| native entity.layout 自身／记录帧 | 0.158 ms | 13.602 ms |
| native entity.convert.topology 自身／记录帧 | 0.072 ms | 2.737 ms |
| Java 几何 marshal 自身／记录帧 | 0.280 ms | 5.861 ms |

CPU、native 与 GPU 表相互嵌套或重叠，不相加；GPU 样本按实际返回调用统计，缺失尾部不补零。线程 CPU 时钟存在约 15.625 ms 的量化，不能把单帧零样本解释成线程没有工作。两份 writer/native/output-cap 丢弃均为零，没有失败帧或检测到的设备丢失。

### 半透明现场以 GPU／追踪为主

该窗口主队列 GPU 区间接近真实帧间隔，PT 模块占其中大部分。JFR 的 581 个渲染线程样本中，349 个落在 `RendererProxy.streamlineFrameEvent`；来源在帧边界调用 `StreamlineRuntime::beginFrame`，其中包含 `slReflexSleep`。这支持存在 pacing 等待，不能将 FRAME_OTHER 的 17.781 ms 自身墙钟全算作 Java 实际计算，也不能把 Reflex 等待自动当作故障。

静态区块快照没有重建或 cache-build，9 份静态记录持续命中，区段排队与在途观测为零，TLAS 16 个实例。当前没有证据支持该现场主要由区块加载、静态全量组织或大量动态 BLAS 主导。

现有探针只把 PT 汇总为一整个 GPU 模块；新增分层路径确实会对多个覆盖面分别运行已有受光路径，但本窗口没有相同场景的随机覆盖对照，也没有逐 PT pass 的 GPU 时间。不能把 21.890 ms 全部指定为新增混合造成的额外开销，仍需受控分段或对照。

### 多光源现场以动态输入 CPU 为主

渲染线程 CPU 接近整帧墙钟，主队列 GPU 只有约 9.350 ms。JFR 渲染线程的主要 native 叶节点为 `EntityProxy.build`（133 样本）与 `queueBuildSourcesV3`（63 样本），还有 `WorldOutlineGeometry.emitPoint`、`collectShapeEdges` 的 Java 调用。不能单凭场景名称认定本次是 GPU 光源采样瓶颈。

该现场每记录帧约 19,377 个 captured-line 来源顶点、11,360 个 PBR 来源顶点、7.37 MB 的 `entity.gpu-upload` 计数字节，TLAS 约 142 个实例。不同格式、原始输入、GPU 输出与传输计数可能重叠，不能将这些字节相加当作总 PCIe 传输，也不能将线顶点直接当作灯的数量。

`Entities::build` 的 `entity.layout` 区间包含未准备几何的 `mcvr::geometry::prepare`、来源层合成及布局整理；前者重新整理位置并运行拓扑协调。单个宽区间尚未区分这些步骤各占多少，13.602 ms 不能全部记到某个拓扑函数。但大量逐帧线／轮廓几何及 native 布局的成本已足以成为优先调查对象，不能通过删轮廓、取消物理发光或跳过必要成对面保护来“优化”。

### 证据覆盖缺口

- 现有元数据缺少当时的相机坐标与各来源对应的光源计数，尚未把两处现场固定成可自动复测夹具。
- `chunk.resident.*` 是间歇观测；分析 JSON 中归一到全部帧的数值不是每帧驻留数量，应使用实际原始观测行。
- NVML 是整卡数据，其他进程和诊断开销未隔离；没有严格前后收益、生成帧动态视觉或长期稳定性结论。
- 启动长未响应是[另一项现场](incident-startup_handoff_delay.md)，本次没有为了复现再次启动。

## 结论

两份可读取的现场已取得，显示应分别沿“半透明的 PT GPU 工作”和“多光源现场的大量动态线／轮廓与 native 拓扑／布局”收敛，尚未实施性能修复或证明光源数量的独立因果。后续先固定世界与相机，再补最小的缺失分段，保留同场景、同查询语义与相同资源生命周期；高视距按使用者要求最后检查。

当前客户端留给使用者操作，没有自动关闭、重启或切换设置。源码、构建与探针身份见[本轮计划](../project/plan-scene_performance.md)，未提交或推送。

### 2026-10-18 继续核验

[后续三场景调查](investigation-three_scene_paths.md)记录发光轮廓来源、生产函数离线实验，以及读取到的异常截图。补查日志发现两次窗口之间删除并重新创建了同名 `New World`；当前存档不自动代表先前半透明夹具。后续不再用同名或同进程推断世界内容相同，原始测量仍保留各自范围。
