# 三个手工场景的定向归因

2026-10-18，继续分析前一日取得的半透明、多光源采样，以及使用者新提供的世界底部截图。本轮区分运行证据、生产函数离线实验与源码推导；没有实施性能修复，不把诊断分段变化或外部原型当作整帧提速。

## 问题

三项表现为普通半透明叠加卡顿、多光源现场卡顿，以及低于世界最低高度后底面／下半天空全黑。初始运行与产物见[首轮采样](investigation-scene_performance_baselines.md)和[底部观察](incident-below_world_sky_darkening.md)。三项不能合并为同一种顶点或光照问题。

## 方法

保留 PID 46560 的原始帧、JFR、配置和日志，读取两张 F2 图像；只将 23:55:19 的截图归到新增黑色现场。静态追踪实际生产者与消费者，用仓库当前 C++ 头文件构建仓库外的有界 CPU 实验。实验没有 Vulkan 设备、游戏逻辑或新客户端，不替换当前包，也不删除轮廓或照明。

临时工具与结果位于 `D:/Workspaces/Scratches/RadianceSemanticsAudit/`：`scene_path_cost_probe.cpp`、`scene-path-cost-probe*.csv`、`coverage_control_flow_probe.cpp`、`coverage-control-flow-probe.csv`。前者执行真实 `lines::prism`、`topology::reconcileAuthored` 与 `composeSurfaceLayers`；后者只将生产 GLSL 控制流转换为 C++ 引用参数，交点与照明为可计数接缝，不执行真实 BSDF 或 GPU shader。

C++ 实验为 MSVC `/O2 /EHsc /std:c++20`，每组 2 次预热与 11 次计时，原始均值、中位数、最小／最大值均保留。游戏与其他进程仍可能占用机器；这些是机制与量级实验，不是安静环境的游戏 A/B，不按它们承诺最终 FPS。

## 发现

### 半透明：确定混合的工作量与实际覆盖率仍须分别测量

原窗口 PT GPU 为 21.890 ms，整帧起点间隔 24.645 ms；CPU 包含大量帧边界等待。共享 `coverage_raygen.glsl` 对背景每层执行原有照明续接，首层之外最多八层确定混合，再使用原随机估计器处理尾部。它没有创建无界 Vulkan 资源，也没有因到达预算而删除后方内容。

生产循环的离线接缝取得以下计数，假定前景是普通覆盖面、后面最终有不透明表面：

| 普通覆盖层总数 | 背景查询次数 | 包含前景的照明路径数 | 随机尾部 |
| --- | ---: | ---: | --- |
| 1 | 1 | 2 | 无 |
| 2 | 2 | 3 | 无 |
| 4 | 4 | 5 | 无 |
| 8 | 8 | 9 | 无 |
| 9 及以上 | 最多 9 | 最多 10 | 有 |

此处的“路径”包含一次表面处理及其原有照明续接，不等于每次一定完成全部反弹，更不是耗时倍数。接缝只验证分支工作规模；实际随机尾部仍可能在一次查询内部拒绝多个覆盖面。切换回随机覆盖、减少反弹或降低确定层数都不是本次已获批准的修复。

尚缺当时覆盖分支命中率、每像素层数与逐 pass GPU 时间。23:30:48 的另一张截图在采样结束约 79 秒后，画面是发光石平台，不能用它证明此前采样时确实进入了哪些半透明分支。也不能排除混合变体的寄存器／内存压力。因此当前确认的是“GPU 追踪较重与可解释的放大机制”，不是已经证明这 21.890 ms 全由分层增加。

### 多光源：实际包含 67 个发光轮廓对象

原日志在 23:31:34 记录 `Applied effect Glowing to 67 targets`，随后才开始多光源采样。该窗口约 134.56 个动态 BLAS 输入、144.56 个 TLAS 实例、19,377 个 captured-line 来源顶点／帧；不同聚合窗口的实例均值不能强行凑成整数。JFR 确认 `ModelPartWorldOutlineMixins` 到 `WorldOutlineGeometry` 的路径在运行。

这条路径逐次合并局部 cube 的 `VoxelShape`、枚举边并提交带姿态的线请求，native 再把每条线扩为 8 个顶点／12 个三角形；随后一般三角形拓扑配对为所有三角形建立位置键与容器。约 19,377 个来源顶点按 LINES 的四个来源顶点／段，对应约 4,844 段的量级；实际模式混合与零透明连接段必须由新的分段确认，不能把这一换算当作已捕获的准确线段数。

生产头文件实验中，4,844 个分离线棱柱分为 128 组时，拓扑协调中位数约 9.36 ms，单纯位置复制约 0.08 ms；合在一组时拓扑约 17.21 ms。与现场 `entity.layout` 的 13.602 ms 同量级，但并未测出现场宽区间内每个子项的准确占比。另一个有序表面层函数即使所有组都不合格也会建立位置索引，离线约 25 ms；现场是否调用及占比未证明，不能把这个数加到游戏帧上。

因此本次“光源越多越慢”至少混入了轮廓生产和拓扑准备。GPU 在该窗口约 9.350 ms，CPU 约 30.811 ms，当前不支持先把 GPU 光源采样当作主因。

### 容器替换必须实测，直接换哈希并不可靠

仓库外的三角形分组原型保留同绕序、反向配对、歧义、退化、非有限值、索引与图元标志；1,500 组固定随机输入与生产实现逐项一致。直接复用当前 `KeyHash` 时，单组大输入中位数约 52.68 ms，反而慢于同轮树形实现约 17.80 ms；不能将“使用哈希”视为自动优化。

为哈希结果补最终位混合的外部原型，在另一次同组对照中约 7.98 ms，对照树形实现约 19.83 ms；128 组时为 4.30／9.40 ms。外部负载和轮次波动保留，没有把两轮拼成一个严格收益。该原型没有进入产品，尚需直接调用方、峰值分配和真实输入回归。

可实施的方向是保留必要配对、减少三角形键的逐项分配，并复用可证明不变的局部轮廓边；姿态、颜色、可见部件与完整几何仍逐帧正确更新。不能跳过配对来恢复楔体，也不能关闭发光轮廓或世界照明制造收益。

### 世界底部：天空显示条件污染传光查询

23:55:19 截图实际为 1920×1080，F3 玩家坐标约 `(23.519, -67.68624, -1.006)`，朝西、yaw 86°／pitch -16.5°；这是玩家位置，不擅自当作相机眼睛位置。可见方块底面大面积全黑与下半天空黑色，客户端仍能正常绘制。

原版黑色天空盘只影响天空绘制。当前两套 PT 的 `isSkyDark` 分支却没有查询用途限制，玩家越过地平线就将所有朝下的天空 miss 设为零，包含世界反弹。由观察者高度改变固定世界的环境照明，是确认的边界缺口；它与太阳被地面遮挡的正常阴影应分开。

修复应将原版的天空显示语义与世界传光分离，沿既有直接成像／传光身份处理，不能凭跳数判断或设置最低亮度。是否完整解释截图中的每个黑色像素，仍待固定姿态的受控渲染对照，不由一次截图宣布通过。

补查排除了一个容易误判的解释：主世界传入的是纯旋转视图，native 只求其逆矩阵，并将真实位置另写入 `cameraPos`。天空 shader 读取 `cameraViewMatInv[3].y`，不能直接把它当作 F3 的绝对 Y。因此不能仅凭玩家低于 -70，就断定当前相机落入大气行星内部；GUI 或第三方特殊视图没有据此自动排除。

### 世界身份与复测缺口

日志在两次性能窗口之间明确记录删除 `New World`，随后创建并进入新的同名世界；同一进程、同名存档不代表同一个世界。当前剩余存档不能自动当成第一份半透明场景的严格复测夹具。原始数据与截图继续保留，后续城市综合检测应固定新的完整输入和相机，不反推旧夹具身份。

## 结论

三组已完成本轮初步盘点，分别收敛到：半透明的 GPU 分层／编译变体成本、多光源现场的动态轮廓与拓扑 CPU 成本、天空显示条件越界影响环境照明。前两项没有整帧优化收益，第三项没有修复后渲染结论；GPU 首次设备丢失根因仍独立，当前进程没有检测到新的设备丢失。

为随后获授权的城市综合诊断，需补齐采样相机／世界状态、拓扑和表面层子分段、逐 PT pass 的 GPU 完成区间。新增计时与原模块区间嵌套，不相加；拆细后的旧宽区间 self 下降也不代表优化。城市输入只读来自授权 Prism，运行和诊断均在项目内，正式窗口等使用者复现后通知才开始。
