# 纯原版城市性能瓶颈诊断

2026-10-20 调查。32 视距的主要瓶颈是渲染线程的实体生产、原生表面层匹配及场景提交；16 视距更接近 GPU／帧推进等待受限。本轮只诊断阶段 6、7 的已验收冻结候选，没有实现产品优化。数据来自有并行负载的单组诊断，不能作为安静环境的绝对性能或优化收益，也不证明阶段 6、7 引起了回归；GPU 时间戳不拆分硬件遍历、着色与调度等待，JFR 样本比例也不等于墙钟占比。

## 问题

使用者报告当前性能不乐观。32 视距的新原版城市初步帧间隔约 56～62 ms，旧带模组城市的 GPU 记录不能直接解释新夹具。候选及来源身份沿用[当前状态](../project/status-current.md)，不重新打包产品。

开始前列出三个可证伪候选：

1. 实体／BER 的渲染、材质状态采集及动态几何生产／提交仍是主要 CPU 工作；几何完全接管并不代表来源回调或真实变化工作消失。
2. 已加载场景的实例／元数据组织与 AS 准备仍随有效内容增长；此前静态路径改进不代表剩余遍历、提交和同步都已消除。
3. GPU 世界 PT／SDK 工作或 CPU 等待限制帧推进；旧 GPU 时间和外部整卡利用率不能排除当前分辨率、资源压力或调度等待。

先检查诊断是否影响接管资格，再用同窗口的 CPU、GPU 与真实帧间隔定性；随后拆分并测量 16／24／32 视距规模。

## 方法

### 输入与证据

产品身份沿用[当前状态](../project/status-current.md)，没有用 Gradle 重包结果替换冻结 JAR。四种设置都恢复 `validations/migration-city_world/result/vanilla-city-fixture.zip`；仅 NeoForge、Radiance 与必要探针，Vanilla PT、RR Balanced、Reflex 2、FG 关闭、4 次反弹、SHARC 开启、区块发光收集关闭，模拟距离始终 32。时间、天气与相机固定，动画和游戏 tick 继续运行；实际实例数仍会变化，不宣称逐帧内容完全一致。自动实例静音、禁抢焦点和输入，不使用 Computer-Use。

入口和命令见[验证说明](../../validations/performance-vanilla/validation.md)。统一证据索引为 `validations/performance-vanilla/result/diagnosis-summary.json`，逐窗原始表、JFR、来源资格和日志在对应案例目录。五个有效案例使用同一探针；首次来源预检单独排除。所有客户端正常保存关闭，没有设备丢失，复制客户端已回收。

| 案例 | 用途 |
| --- | --- |
| `r32-1080-20261020-135930` | 32 视距同窗定性与主要归因 |
| `r32-1440-20261020-140656` | 分辨率定性；后段有明显干扰 |
| `r24-1080-20261020-141424` | 24 视距阶段／工作量；有本线程分析任务重叠 |
| `r16-1080-20261020-141906` | 16 视距阶段／工作量 |
| `r24-1080-20261020-142408` | 不与本线程分析任务重叠的补充 FRAME_ONLY |

### 计时与诊断有效性

每次至少预热 60 秒，并要求 Java 与 native 构建队列连续平静 10 秒。依次取 FRAME_ONLY 30 秒、TIMED 10 秒、JFR_ONLY 30 秒；补充案例只取 FRAME_ONLY。全部 STATUS 完整，无丢帧表、丢事件、容量溢出或 CPU 分区错误。不裁尾；GPU 未返回的边界帧不补零。

- Java 主循环与渲染同在 `Render thread`，客户端 tick 单列；集成服务器另在 `Server thread`。线程活跃时间来自 ThreadMXBean，正量子为 15.625 ms，只解释整窗平均。JFR 的线程 CPU 负载按 28 个活动逻辑处理器归一化，依据 [OpenJDK 21 实现](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/share/jfr/periodic/jfrThreadCPULoadEvent.cpp)。
- Java self 是互斥墙钟分区，包含等待；native 是这些分区内部的下钻，不能相加。GPU 主队列、模块和 pass 也嵌套；时间戳的含义参见 [Vulkan profiling](https://docs.vulkan.org/guide/latest/profiling.html)。
- FRAME_ONLY 仍保留原有主队列时间戳。`baseGpu` 用完全落在同一墙钟窗口内的 1 秒完成桶加权，不是逐帧 token 配对；TIMED 的原始 GPU 行另有帧 token。两者均不代表显示扫描输出。
- 探针的生产者包装及 `LevelRenderer` 访问器会触发 adr-9 自动退回。已在专用配置中关闭这些观察器，保留产品保护；有效案例的 PARTS、BAKED、STATIC_STATE 及已观察生产者未因 probe 退回。首次 `r32-1080-20261020-135054` 只作为工具预检，不参与结论。
- JFR CLI 默认只导出 5 层，曾掩盖调用方；现按执行样本深栈、其他事件浅栈分开导出，跳过本轮不用的 allocation 栈。32／1080 有 586 个渲染线程样本，其中 93 个原录制栈仍截断；JNI 只定位到入口，C++ 内部由 native 计时补充。

### 噪声

原始 `noise.jsonl` 逐窗记录整卡 NVML 与游戏进程，WDDM 不提供这里所需的可靠进程独占显存／GPU 占比。最初入口匹配遗漏了新式 NeoForge 客户端，后补现代启动入口；`gpu-process-supplement.json` 用创建时间和仍存活快照确认 GLASS PID 38504 从 13:35:05 起连续覆盖所有窗口。这个补充证明进程存在，不反推它过去的 GPU 占比；短暂遗漏的其他进程仍是覆盖缺口。

| 窗口 | 整卡 GPU 平均／最高 | 明确标注 |
| --- | --- | --- |
| 32／1080 FRAME_ONLY、TIMED、JFR_ONLY | 50.8／64%、54.0／67%、53.5／85% | GLASS 与 MCP 进程并存 |
| 32／1440 FRAME_ONLY、TIMED、JFR_ONLY | 68.6／82%、61.7／100%、99.4／100% | 后两窗明显变化；JFR 中 MCP PID 55288 出现 |
| 24 首轮 FRAME_ONLY、TIMED、JFR_ONLY | 逐窗见索引 | 深栈导出任务 14:15:43～14:17:57 覆盖前两窗及 JFR 开头；已停止并改为分开导出 |
| 24 补充 FRAME_ONLY | 34.8／41% | 无本线程分析重叠，GLASS 仍在 |
| 16 三窗 | 逐窗见索引 | FRAME_ONLY 与 TIMED 的 GPU 完成时间明显变化，不视作插桩提速 |

32 视距整卡显存约 15,400～15,700 MiB，接近 16,376 MiB 容量；VMA 总字节包含其他内存类型，不能全归为独占显存。没有改动系统权限，也未取得分页、硬件计数器或 BVH／ALU 分解。精确的分辨率比例、GPU 构建异常放大、尾部帧及收益预测需安静环境复测，本轮不追加这种实验。

## 发现

### 同窗定性

下面使用轻量 FRAME_ONLY，GPU 为同墙钟窗的原有完成桶均值；详细 TIMED 也支持 32 视距 CPU 主导。

| 设置 | 平均帧间隔／真实 FPS | p95／p99 ms | 主循环墙钟／CPU 活跃 ms | GPU 完成 ms | 判断 |
| --- | --- | --- | --- | --- | --- |
| 32，1080p | 62.93／15.89 | 80.03／93.78 | 62.77／61.68 | 30.30 | CPU 主导 |
| 32，1440p | 59.92／16.69 | 76.80／87.20 | 59.78／59.38 | 37.21 | CPU 主导，GPU 预算也明显 |
| 24，1080p 补充 | 49.09／20.37 | 58.99／64.82 | 48.95／48.84 | 15.93 | CPU 主导 |
| 16，1080p | 23.39／42.76 | 25.99／26.96 | 23.30／10.41 | 22.38 | GPU／帧推进等待主导 |

32／1080 TIMED 是帧间隔 64.70、CPU 活跃 63.10、153 个有效 GPU 帧均值 30.65 ms；32／1440 TIMED 是 70.82、67.01、139 个 GPU 帧 49.18 ms。1440p 的 JFR 窗则变为帧间隔 134.45、CPU 活跃 84.26、GPU 完成约 130.40 ms，且整卡几乎持续 100%：这是受明显干扰的窗口，不能代表正常 1440p，也不能把全部变化归给 JFR。

### CPU 排序与下钻

32／1080 TIMED 的互斥 Java self 均值，百分比以该窗真实帧间隔为分母。native 下钻已经包含在对应父项内。

| 顺序 | 工作 | ms／帧 | 占帧间隔 | 下钻与可信度 |
| --- | --- | ---: | ---: | --- |
| 1 | 实体生产／原 renderer 与提交外围 | 20.92 | 32.3% | 原方法外层计时，高；不是全部可删除的顶点转换 |
| 2 | 场景准备、记录与提交 | 12.59 | 19.5% | native world-prepare 9.61 ms 包含其中，高 |
| 3 | 世界收尾与其余世界工作 | 11.90 | 18.4% | native entity batch build 11.82 ms，其中层匹配 7.84、拓扑 1.86、层上传记录 0.48 ms，高 |
| 4 | 通用几何整理／JNI | 4.09 | 6.3% | 原生 sources 入口约 2.12 ms 包含其中，中高 |
| 5 | 客户端 tick | 4.01 | 6.2% | 与异步服务器成本分开，高 |
| 6 | 材质状态设置／清除／备份／恢复 | 3.11 | 4.8% | 实际状态路径；不代表这些语义可以删，高 |
| 7 | acquire／退休与重置 | 2.93 | 4.5% | 实际 swapchain acquire 0.0048、fence wait 0.0011 ms，余项尚未进一步拆分 |
| 8 | BER | 1.96 | 3.0% | 外层自身耗时，高 |

场景准备中的静态实例追加 1.33、元数据初始化 2.64、staging copy 1.43、TLAS 记录 1.40 ms 是子项；其中初始化在 1440p 仅 0.66 ms，不能把单窗数值当固定线性成本。普通 descriptor materialize/bind 约 0.014 ms，SBT allocate/copy/record 约 0.60 ms，不是当前首要热点。

JFR 深栈将 137／586 样本归到 native submit，128 到 native entity build，127 到实体生产，134 到 client tick；样本不能换算成上述毫秒。32／1080 渲染线程约占一个逻辑核心 97.5% 的活跃预算，集成服务器约 27.5%。该 JFR 窗 GC pause 合计 57.18 ms／30 秒，最大 21.27 ms；没有达到阈值的渲染线程 Java monitor／park 报告。结合已测锁等待，GC 或共享锁不是当前稳态主因；不排除未观测的 native／驱动尾部等待。

### GPU 排序

同窗有效 GPU 帧的阶段均值，父区间不再与子项相加。1440p TIMED 有过渡干扰，分辨率比例不据此定案。

| 区间 | 32／1080 ms | 32／1440 ms | 范围 |
| --- | ---: | ---: | --- |
| 主队列整体 | 30.65 | 49.18 | 包含以下工作及未分离的屏障／调度 |
| 世界追踪 pass | 14.50 | 30.30 | 遍历＋着色联合，含 pass 内准备／屏障 |
| TLAS 构建 | 4.60 | 5.64 | 时间戳完成区间，可能受驻留／调度影响 |
| 动态转换 | 2.98 | 2.25 | 不是纯 ALU busy 时间 |
| 动态 BLAS | 2.32 | 1.21 | 不与 native CPU build 互相相加 |
| RR＋超分 | 1.40 | 3.08 | 同一个 SDK evaluate，内部未拆分 |
| 上传命令缓冲 | 0.96 | 见原始表 | 独立父区间，不是 PCIe 流量实测 |
| SHARC 更新／解析 | 0.27／0.13 | 见原始表 | 独立子范围 |
| UI／最终合成 | 0.24／0.018 | 见原始表 | 命令缓冲完成；不含显示扫描 |

CPU present API 约 0.28 ms，不能代表 GPU 扫描输出。没有获得遍历／材质 shader 各自占比，也没有 SDK 内部 RR／SR 拆分，这些是明确缺口。

### 规模与工作量

计数来自 TIMED；24 首轮有上述分析干扰，因此只用其工作量与热点量级，帧时间采用补充窗口。

| 项目 | 16 | 24 | 32／1080 |
| --- | ---: | ---: | ---: |
| 槽位容量 | 26,136 | 57,624 | 101,400 |
| 有效静态区段 | 8,227 | 16,890 | 28,820 |
| 静态几何记录 | 14,540 | 28,677 | 47,560 |
| TLAS 实例 | 8,834 | 18,965 | 31,602 |
| 刚性部件实例 | 591 | 1,954 | 2,597 |
| 表面层所有者／附着三角形 | 0／0 | 59／5,400 | 62／5,400 |
| 每帧准备顶点 | 约 6 | 39,906 | 41,274 |
| 元数据逻辑上传 MiB／帧 | 6.66 | 13.66 | 22.37 |
| 实体 CPU self ms | 2.15 | 17.81 | 20.92 |
| 层匹配 CPU ms | 0 | 7.78 | 7.84 |

16→32 有效区段约 3.50 倍、TLAS 约 3.58 倍；实体 self 约 9.7 倍，并在 16→24 出现需要层合成的真实内容。因此高视距退化不只是空容量或统一接管层的固定费用。静态缓存仍命中，每帧避免约 19.23 MiB 静态复制，但总元数据仍上传约 22.37 MiB，表明复用没有消除完整场景的动态组织。

32 的 GPU 转换／BLAS／TLAS 比 24 明显放大，同时整卡显存逼近容量；现有数据不能区分驻留迁移、调度干扰与算法成本。不能把这部分全部承诺为可优化计算。`entity.rigid.new-input` 的 count 是顶点数，约 1,215／帧，不是新模型数；不据此编造缓存 46% 失效的结论。

## 结论

前三个候选的结果分别是：实体与动态提交为主要 CPU 成本；静态组织仍有规模成本但不是全部原因；GPU 在 16 视距以及受强干扰的 1440p 窗口能成为限制，不能全局排除。

建议下一轮只选一个原型，优先第一项。本表的目标收益是实验预算，不是已测结果；不能相加为整帧承诺。

| 优先级 | 建议 | 可测收益范围／上界 | 主要风险与依据 |
| --- | --- | --- | --- |
| 1 | 将已声明模型的同表面层绑定推进到稳定局部拓扑，避免每帧在最终三角形上重新寻找对应关系 | 首个原型目标 2～6 ms；单独匹配成本上界约 7.8 ms，也可能因成本转移无净收益 | [surface_layers.hpp](../../components/native_renderer/src/core/render/surface_layers.hpp) 当前构建有序映射并匹配全部候选；必须保留眼睛发光、cutout、受击染色、颜色与层顺序。按 adr-9 的显式资源／实例合同实现，未证明来源继续退回 |
| 2 | 对同一高耗时来源，减少实体生产中的临时捕获、状态重放与提交工作；先定向区分原 renderer 与可省的重复部分 | 探索目标 3～8 ms；20.9 ms 不能全部当可删除预算，仍需验证覆盖 | 不缓存上一帧最终顶点，不冻结动画；使用 adr-8／9 的局部资源＋姿态／外观，而非扩大类名缓存 |
| 3 | 稳定静态索引和增量元数据，单独评估 TLAS 的真实变化与 GPU 驻留 | CPU 原型目标 1～3 ms；GPU 收益当前无法可信估计 | 不以相机剔除减少全 PT 场景；保留代际、历史、资源退休。先分离显存／调度干扰，再决定 AS 路线，遵守 adr-11 的完整内容范围 |
| 后续 | 世界 PT 遍历／着色拆分后再选 GPU 算法 | 本窗 pass 14.5 ms 是整个范围，不是可兑现收益；现在不报百分比 | 需要更细 GPU 证据；不能通过降采样、削几何或改光照语义制造收益 |

本轮没有产品／着色器／原生逻辑修改，不推进第三方，不提交、推送或投放 Prism。已把 `local.toml` 的同一 Voxy 输入改指已核对一致的 Published 副本，未改 EULA。阶段 0～3、6、7 的使用者视觉通过继续有效；GPU 根因、严格 FG 后 GUI、长期稳定性和公开二进制许可仍独立开放。诊断至此结束，后续优化由使用者决定。
