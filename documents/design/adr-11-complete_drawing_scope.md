# 全绘制范围、版本证明与统一负责方

## 状态

已接受

使用者于 2026-10-20 修订范围措辞。本决定取代 [adr-8](adr-8-rendering_semantic_takeover.md) 的范围与完成判据；其余来源语义、完整世界 PT、GUI／呈现分离、生命周期和不依赖 Flywheel 的原则继续沿用。公共合同与自动退回按 [adr-9](adr-9-portable_takeover_contracts.md)，原版优先与阶段顺序按 [adr-10](adr-10-vanilla_first_takeover.md)。当前 Goal 及阶段 3 的实施边界不变。

同日后续使用者决定暂停各阶段性能对比，阶段 3 城市六次计时不再作为门槛；正确性和合并目视交付继续，执行安排见[当前计划](../project/plan-render_takeover.md)，不改变本决定的绘制范围。

2026-10-20 的原版 renderer 替代与两节推进顺序由 [adr-12](adr-12-vanilla_renderer_replacement.md)补充，完整范围不变。

## 背景

“几乎全部合法绘制”无法给出明确缺口上限，也未区分版本已验证与元数据声明。按来源各建一套实现还会复制同类状态和执行规则，妨碍统一核销与跨版本移植。

## 决策

### 范围与版本

目标是当前游戏版本，以及已纳入依赖在各自已验证版本范围内的所有绘制。依赖及实际版本以 Target 的 target.properties 和根 inputs.toml 为准，不把未登记模组、任意未来版本或未证明的改动自动列为已支持。

每个依赖在[依赖登记](../reference/dependency-rendering.md#兼容范围与证明方式)记录兼容范围、验证方式及证据缺口。接口稳定的加载器按实际接口差异核对，并测试候选范围两端，争取扩大已验证范围；Veil 等深度修改原版的依赖逐版本验证和适配。模组元数据只声明有对应证明的范围；范围外版本和未登记改动按 adr-9 退回，保留日志原因，不能将退回等同直接接管通过。产品原有硬依赖若不能解析或 Loader 已拒绝启动，不承诺可以由渲染退回使其运行。

本次只修改文档，不调整版本、依赖声明或来源资格；登记中须明确区分现有声明与已取得的证明，未闭合范围进入后续对应兼容批次。

### 按绘制类型统一管理

接管按绘制类型组织：地形／流体、刚性／形变网格、线点、粒子／程序化请求、表面／附加层、GUI／文字、离屏／屏幕效果与呈现。同类绘制由同一套合同、状态、依赖、执行和退休机制管理，原版及各模组只经薄来源适配器接入，不为单个来源复制渲染器。

实例化是基础能力，允许共享模型、多实例以及单个对象姿态或外观变化；真实形变与拓扑变化仍显式更新。公共合同保持版本可移植，不携带游戏或模组对象，为跨版本移植保留边界，不为未支持的版本提前实现适配器。

### 完成判据

在计划定义的固定巡检路线中，没有负责方的绘制计数必须为 0，覆盖表没有未知；每项绘制都有明确结论：直接接管、由 Radiance 的 Vulkan 按原样光栅执行，或经使用者批准的差异。负责方存在、输入完整与输出语义对照是三个独立条件，不能只登记一个名字就核销。

直接接管可以接受真实动态顶点请求，不等于全部几何零顶点生成；前提是图元、状态、资源、程序、目标、依赖和执行归属均由合同完整表达。仍靠不明兼容规则接收的捕获只是迁移状态，不能作为最终的第四种结论。Vulkan 光栅结论只用于既有合同允许的 GUI、离屏和屏幕内容；不借此新增世界后置光栅。

巡检登记同时覆盖声明来源与实际请求。固定路线的零计数不能证明未执行分支不存在，因此注册表中未在路线出现的绘制还要有独立用例或明确的不适用证据，不能静默删项。零未知是全部范围最终完成的门槛，不能提前写成阶段 3 已完成后续阶段。

## 后果

需要按依赖范围和绘制类型维护同一份覆盖登记，并逐阶段补齐请求计数。阶段 3 的原版来源功能、性能和合并目视交付继续执行；本次不新增产品、探针或计数实现，不开始其他阶段。未知 GPU 根因、严格 FG 后 GUI、长期稳定性和公开二进制许可仍单独核销。
