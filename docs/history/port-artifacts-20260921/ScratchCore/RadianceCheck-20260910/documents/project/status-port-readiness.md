## Radiance：最影响你使用的事情

原版的主要世界绘制、材质纹理、云、两套内置光追方案和画质控制仍有对应实现。文字、星空、透明物体和轮廓的处理有主动变化，不能只按上游同名文件是否存在判断丢失；也不能仅凭接线存在就保证画面一致。[E1：覆盖索引、M-06–M-13]

| 必须处理的适配 | 从 Fabric 1.21.4 到 NeoForge 1.21.1，加载入口、Minecraft API 和加载窗口衔接确实需要适配；这不证明每一处大范围改写都必要。 |

**MCVR 的治理资料单独处理：** 当前组件旧 AGENTS 已标为历史指令，原生构建入口和技术资料仍在；组件 `.github` 中只发现资助配置，没有工作流。后续用已有导入清单明确旧治理／自动化的保留、适配或退役理由，保留原生构建测试能力；整仓承接不授权整理 Git 历史。[E9]

建议分四个小批次收敛：**①先完成下述基础使用批次；②借现有清单补齐 MCVR 各类内容的来源与去向，只补明确缺口；③每次围绕一项能力说明修改目的，保留有效修复，定向缩小或修正有反证的改写，兼容工作仍按原模组族顺序；④单独统一模板外层与 properties，先对照旧配置的实际结果，不同时改变画面。** 不进行全仓覆盖或重新实现。

原版基线、你名下 fork 的远程保存版本、带未提交成果的本地工作树是三份不同对象。本文判断的是最后一份；远程只作对照，不覆盖本地。具体绑定见 E9。

## 后续产品推进批次（工程与历史整合之后）

**目标：交付一个可由你独立体验的 Windows / NeoForge 1.21.1 基础版本，安装和验证过程不依赖源码开发目录。** 保持已确定的 Radiance＋vulkan-renderer 整合路线。通过只代表下列范围通过，不代表所有光影、硬件和兼容模组都完成。

1. **先验证交付前置。** 沿用已确定的“正式 Mod JAR＋规定 NVIDIA DLL、全新目录首次启动、保留官方加载流程和 Vulkan 路线”。我先分析并验证生产安装入口；不能用额外启动补丁、预写配置或要求首次重启来悄悄降低目标。加载先后顺序是本批技术难点，复杂度高于两处局部修复；若证明确实需要放宽安装要求，应先提交具体限制和用户体验方案，届时才需要你作产品决定。
2. **修两项确定缺陷。** 正确处理 DLSS 结果，补足材质资源释放。它们是保持既定行为的技术修复；交付入口和加载画面的内部实现可能需要调整，目标是达到已有要求，不改变主世界光影设计。对加载画面先作定向检查，不仅因使用 CPU 就全面重写。
3. **走真实使用流程。** 在三个互相独立的新目录中各冷启动一次，由你确认菜单、进世界和退出；其中一次用固定场景体验约 10 分钟，观察方块、流体、实体、文字与菜单，并做窗口切换、返回菜单和重新入世。默认画质及该显卡支持的 DLSS 设置分别记录；一次进入菜单不算完成。

**为什么先做这批：** 安装入口决定你能否脱离开发环境使用；错误处理和资源回收会干扰后续判断。先稳定有限的基础流程，才能分辨后面出现的问题来自本体还是兼容模组。这也沿用先基础、后逐模组族的既定顺序。[K2]

本批不包含：额外 Target、Linux、完整兼容组合、全面恢复上游效果、旧存档转换、一般性能重构，以及截图专项修复。首批通过不等于原先“基础族全部通过”，不会自动跳过基础剩余项进入兼容族。已确定的兼容工作仍保留；未知模组的普遍兼容不自动加入。
